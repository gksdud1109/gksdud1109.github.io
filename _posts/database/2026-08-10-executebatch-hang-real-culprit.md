7주 전에 [트러블슈팅 글](/posts/oracle-executebatch-hang-debugging/)을 하나 발행했다. 데이터 레이크에서 읽어온 대량 데이터를 캐시 테이블에 적재하는 배치가 예외도 타임아웃도 없이 멈추는 문제였고, 결론은 이랬다.

> IDENTITY 테이블에 executeBatch로 적재할 때만 멈춘다. 행별 `executeUpdate`로 바꾸니 정상 완료됐다.

그 결론이 틀렸다.

진범은 IDENTITY도 executeBatch도 아니었다. WAS가 JDBC 드라이버를 치환해 물려둔 2009년산 SQL 로깅 라이브러리였고, 내가 해결이라 부르며 발행한 행별 `executeUpdate`는 우회였다. 그 우회가 6배 느린 상태를 7주 동안 고착시켰다.

이 글은 그 정정 기록이다.

## 1. 그때는 무엇을 근거로 그렇게 썼나

당시 판단이 아무 근거 없이 나온 것은 아니었다. 나는 같은 환경에서 되는 코드와 안 되는 코드를 1:1로 대조했고, 이렇게 좁혔다.

```text
SELECT 1 통과
DELETE 통과
COMMIT 통과
INSERT executeBatch 구간에서 정지
```

커넥션은 살아 있었고, 락도 아니었고, IDENTITY 채번 자체는 행별 INSERT에서 멀쩡히 동작했다. 남은 통제된 차이가 batch 호출 경로 하나였다. 그래서 그 경로를 지목했다.

원글에도 단서는 달아뒀다. 항상 충돌한다는 뜻이 아니고, 내부 메커니즘은 단정하지 않는다고 썼다. 그 신중함 자체는 틀리지 않았다.

**틀린 것은 두 가지다.** 첫째, 메커니즘을 모르는 상태에서 executeBatch라는 이름을 원인 자리에 놓았다. 둘째, 증상이 사라진 우회를 해결로 승격시켰다.

## 2. 왜 7주가 걸렸나

가장 뼈아픈 부분이다. 헤매서 오래 걸린 게 아니다. **우회가 작동했기 때문에 추적이 거기서 끝났다.**

증상이 사라지면 티켓이 닫힌다. 배치는 매일 돌았고 아무도 불평하지 않았다. 그렇게 7주가 지났고, 다시 열게 된 계기는 성능이었다. 행수가 늘면서 같은 배치가 8분을 넘겼고, 뒤에 붙은 판정 배치의 마감 시각을 위협하기 시작했다.

여기서 이상한 관찰이 하나 나왔다. 행수가 거의 같은 사흘의 소요가 401초에서 501초까지 25퍼센트나 흔들렸다. 데이터 증가만으로는 설명되지 않는 폭이었다.

## 3. 가설 다섯 개를 태우고 나서야 덤프를 떴다

재추적에서 세운 가설과 각각을 가른 실험이다.

| 가설 | 판별 실험 | 결과 |
|---|---|---|
| IDENTITY 채번이 원인 | IDENTITY 없는 그림자 테이블과 2×2 대조 | 둘 다 느림. 무죄 |
| executeBatch 자체가 원인 | (실험 불가) | 이름일 뿐 메커니즘이 아님 |
| 패킷 크기, MTU | chunk를 1로 줄여 페이로드를 행별과 동일하게 | 여전히 멈춤 |
| queryTimeout과 batch의 상호작용 | 선례와 해당 축만 대조 후 제거 | 여전히 멈춤 |
| 좀비 세션의 미커밋 행 | 블로킹 세션 조회, 재시작 후 단일 실행 | 재현되지 않음 |

두 번째 가설에서 페어 프로그래밍 중 확정이라는 결론이 나왔을 때, 나는 되물었다. executeBatch 자체가 어떻게 원인일 수 있는가. 표준 API가 원래 고장나 있을 리 없다. **X 자체가 원인이라는 말은 가설이 아니라 증상에 붙인 이름이다.** 메커니즘을 한 문장으로 대지 못하면 아직 아무것도 모르는 것이다.

다섯 개를 다 태우고 나서야 스레드 덤프를 떴다. 3줄로 끝났다.

```text
at ... (DaoInfo.java:112)                ← 여기서 정지
at ... (AroundProfiler.java:19)
at com.sun.proxy.$Proxy6.addBatch(...)   ← JDK 동적 프록시
```

우리 코드도 아니고 Oracle 드라이버도 아니었다. `libs/` 폴더에 들어 있던 log4sql이라는 SQL 로깅 라이브러리였다.

## 4. 어떻게 끼어들었나

Spring AOP가 아니다. 진입점 자체가 갈아끼워져 있었다.

```text
WAS 설정: driverClassName = core.log.jdbc.driver.OracleDriver
    ↓ 드라이버 치환. 실드라이버에 위임
PreparedStatement = Proxy.newProxyInstance 로 감싼 JDK 동적 프록시
    ↓
모든 JDBC 호출이 프로파일러를 통과
```

7주 동안 눈에 띄지 않은 이유가 있다. 이 jar는 빌드 도구의 의존성으로 선언된 게 아니라 `libs/*.jar`를 폴더째 클래스패스에 넣는 방식이었다. 의존성 리포트에 뜨지 않는다. 활성화도 코드가 아니라 WAS 설정 한 줄이다. 로그에 SQL이 찍히면 ORM이 찍는 줄 안다.

다만 레포에 흔적이 전혀 없었다는 말은 사실이 아니다. 그 드라이버 클래스명은 테스트 설정 세 곳과 온보딩 문서에도 적혀 있었다. **숨어 있던 게 아니라 아무도 연결하지 않았을 뿐이다.** 이쪽이 더 정확하고 더 뼈아프다.

## 5. 메커니즘: 반환 타입이 리셋 분기를 가른다

`javap`으로 바이트코드를 열어 세 가지를 확인했다.

```java
// 인덱스를 무시하고 무조건 append
private void saveQueryParamValue(int position, Object v) { parameterValues.add(v); }

// 누적 리스트를 비우지 않는다
public void addBatch() { preparedStatement.addBatch(); }

// 비우는 곳은 여기뿐
public void clearParameters() { ...; parameterValues = new ArrayList(); }
```

`setString(1, ..)`, `setInt(2, ..)`가 덮어쓰기가 아니라 계속 쌓인다. 그리고 로그 렌더 루프는 `?` 개수가 아니라 **누적 배열 길이 전체**를 순회하고, `?`가 동나면 버퍼를 문자열로 만들어 자기 자신에 다시 붙인다. 초과 파라미터 하나당 대략 2배다. 이게 기하급수의 실체였다.

여기서 마지막 조각이 풀린다. **행별 `executeUpdate`는 왜 멀쩡했나.**

프로파일러는 반환값이 `Integer`나 `ResultSet`일 때만 로그 분기를 타고, 그 분기 끝에서 누적 리스트를 비운다.

- `executeUpdate()`는 `Integer`를 반환한다. 행마다 리셋되니 선형이다.
- `addBatch()`는 `void`를 반환한다. 그 분기를 아예 타지 못해 리셋 없이 누적만 된다.

7주 전 내가 관측한 비대칭, 즉 배치만 멈추고 행별은 되던 현상이 여기서 전부 설명된다. 나는 그 비대칭을 정확히 봤지만 원인을 잘못 짚었다.

그리고 하나 더. 그때 이건 hang이 아니었다. **기어가고 있었다.** 10행 처리에 175초였다.

## 6. 해결은 한 줄

```kotlin
ps.addBatch()
ps.clearParameters()   // executeUpdate가 자동으로 하던 리셋을 batch 경로에 수동으로 넣는다
```

표준 JDBC API다. 리플렉션도, 전역 설정 변경도, 인프라 요청도 필요 없다. 내가 만든 PreparedStatement 하나에만 영향을 준다.

원인을 규명한 뒤 되는 선례로 삼았던 다른 배치를 다시 열어봤다. **같은 한 줄이 이미 있었다.**

이걸 놓친 단서라고 부르는 건 사후확신이다. 로깅 라이브러리의 존재와 누적 동작을 모르는 상태에서 `addBatch(); clearParameters();`는 평범한 JDBC 위생 코드고, 일반 드라이버에서는 사실상 아무 일도 하지 않는다. **이 줄은 메커니즘을 먼저 안 뒤에야 의미를 갖는다.**

그래서 여기서 가져갈 교훈은 꼼꼼히 보라는 게 아니다. 선례와 대조할 때 비교 축을 미리 정하지 말라는 것이다. 나는 queryTimeout이라는 가설을 세운 뒤 그 축만 대조했다. 어느 줄이 결정적인지는 원인을 알기 전에는 알 수 없으니, 차이를 전부 나열하고 나서 좁히는 편이 빠르다.

## 7. 숫자

정기 배치 기준으로 잰 값이다. 약 36만 행 적재.

| | 개선 전 | 개선 후 |
|---|---:|---:|
| INSERT | 394초 | 66초 |
| 배치 전체 | 435초 | 101초 |
| 행당 비용 | 1.074 ms | 0.178 ms |
| DB 왕복 | 약 36만 회 | 약 370회 |

INSERT 기준 6배다. 부수 효과도 둘 있었다.

**변동성이 사라졌다.** 기존에는 같은 일감이 401초에서 501초까지 흔들렸다. 왕복이 36만 회라 인접 배치와의 경합에 그대로 비례했기 때문이다. 왕복이 370회가 되면서 경합 민감도 자체가 없어졌다.

**증가 추세도 꺾였다.** 이 캐시는 1년 롤링 윈도우라 행수가 계속 는다. 50만 행이면 기존 단가로 12분에 가까워 마감을 위협하지만, 개선 단가면 80초 안쪽이다.

진행 로그도 결론을 뒷받침했다. 5만 행 구간별 소요가 8276, 7498, 7456, 7420, 7471, 7404, 7347 밀리초로 평평했다. 누적이 살아 있었다면 뒤로 갈수록 급증해야 한다. 호출당 비용이 상수가 됐다는 게 실데이터로 확인된다.

## 8. 실험을 안전하게 설계한 부분

상용과 스테이징이 DB를 공유하는 환경이라 실테이블로 실험할 수 없었다. 게다가 이 캐시가 비면 보상 로직이 전 사용자에게 최고 확률을 주는 구조여서, 빈 캐시는 곧 금전 사고다.

- **그림자 테이블로 격리했다.** `CREATE`만 필요하고 롤백은 `DROP` 한 줄이라 승인 문턱이 낮다. 실테이블에는 `SELECT`만 한다.
- **쓰기 대상에 불변식을 걸었다.** 테이블명 오타는 에러 없이 커밋되기 때문이다.
- **결과 행수를 검증했다.** 과거 증상이 조용한 미적재였던 터라, 행수를 세지 않으면 0행을 3초에 넣고 성공으로 오독한다. 실제로 적대적 리뷰에서 이 지적이 나왔다.
- **단일 실행 가드를 넣었다.** 2회차가 1회차의 미커밋 트랜잭션에 락 대기로 걸리면 로그상 hang과 구분이 안 돼 결론 자체가 오염된다.

배포 직전 리뷰에서 블로커도 하나 잡았다. 검증 실패 경로에 명시적 `rollback()`이 없었다. `use{}`는 `close()`만 부르고, 반납 시 롤백 여부는 커넥션 풀 구현마다 다르다. 굴리지 않으면 열린 트랜잭션이 커넥션에 남아 같은 풀의 다른 사용자가 커밋해버릴 수 있다. 안전 실패라고 주석까지 달아둔 경로가 정반대로 작동할 수 있었다.

## 9. 배운 것

1. **증상이 사라진 것과 원인을 아는 것은 다르다.** 7주를 잃은 진짜 이유는 헤맨 게 아니라 우회가 성공해버린 것이다.
2. **hang이면 스레드 덤프가 1순위다.** 가설 다섯 개를 태운 시간 전부가 덤프 한 번으로 대체 가능했다. 로그는 지나간 지점만 알려주고 멈춘 지점은 원리적으로 알려주지 못한다.
3. **멈춘 것과 느린 것을 구분하라.** 간격을 두고 세 번 덤프해 프레임이 움직이는지 본다. 이번 건은 hang이 아니라 기하급수 지연이었다.
4. **X 자체가 원인이라는 말은 라벨이지 가설이 아니다.** 메커니즘을 한 문장으로 대지 못하면 실험 설계도 못 한다.
5. **발행은 종결이 아니다.** 틀린 결론을 공개해두면 다른 사람도 같은 우회로 인도된다. 정정할 의무가 남는다.
