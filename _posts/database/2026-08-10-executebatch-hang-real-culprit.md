> 업무 식별자와 테이블명은 일반화했다. 코드는 호출 순서를 설명하기 위한 예시이며, 성능 수치는 당시 정기 실행 기록을 기준으로 한다.

이벤트에 사용할 구매 이력을 데이터레이크에서 읽어 서비스 DB에 적재하는 작업을 맡았다. 적재가 끝난 데이터는 뒤이은 판정 배치에서 사용했다. 데이터를 빨리 넣는 것뿐 아니라, 다음 작업이 불완전한 스냅샷을 읽지 않게 하는 것도 중요했다.

처음에는 JDBC 배치로 INSERT하려 했지만, 개발 환경에서 실행하면 로그가 끊기고 오랫동안 끝나지 않았다. 오픈 일정이 가까워 행별 `executeUpdate()`로 우회했다. 이 방식은 적재를 완료했고 다음 작업 전까지 시간 여유도 있었다.

그런데 운영하면서 실행 시간의 편차가 커졌다. 건수 증가만으로 설명하기 어려워 우회했던 배치 경로를 다시 조사했다. 그 결과 DB가 아닌 SQL 로깅 프록시에서 비용이 커지고 있다는 것을 확인했다.

## 행별 INSERT가 됐다는 사실로 원인을 설명할 수는 없었다

[이전 글](/posts/oracle-executebatch-hang-debugging/)에서는 IDENTITY가 있는 테이블의 batch 경로에서 문제가 생긴다는 관측을 남겼다. 행별 INSERT가 되므로 그 경로를 피하는 쪽으로 결론을 냈다.

당시 확인한 것은 커넥션 획득, 간단한 SELECT, DELETE, COMMIT이 동작하고 batch 적재 구간에서 오래 걸린다는 정도였다. IDENTITY와 `executeBatch`의 내부 동작을 원인으로 특정한 것은 아니었다.

재조사에서는 실제 테이블에 반복해서 쓰지 않도록 같은 Oracle 안의 비교용 테이블을 사용했다. 쓰기 대상 검사와 단일 실행 가드를 두고, 실행 후 행 수도 대조했다. 별도 DB로 완전히 격리한 실험은 아니었다.

| 의심한 원인 | 확인한 방법과 결과 |
|---|---|
| IDENTITY 채번 | 자동 채번이 없는 비교용 테이블에서도 batch 경로가 느렸음 |
| 한 번에 보내는 크기 | batch 크기를 1로 줄여도 지연이 남아, 큰 요청에서만 발생하는 문제로 설명되지 않았음 |
| queryTimeout 설정 | 설정을 제거해도 지연이 남았음 |
| 미커밋 작업의 잠금 | 블로킹 세션 조회 권한이 없어 직접 확인하지 못함 |

이때 `executeBatch` 자체가 원인이라는 설명도 나왔지만, 어느 구현의 어떤 동작이 느린지 설명하지 못했다. 호출 이름만 바꿔서는 더 좁힐 수 없었다.

## 스레드 덤프에서 DB 앞의 로깅 코드를 발견했다

진행 로그를 더 잘게 나누고, 실행 중인 서버에서 스레드 덤프를 확보했다. 느려진 경로에는 SQL 로그를 만드는 프록시 코드가 있었다. 특히 DB로 batch를 보내기 전 `addBatch()` 호출 경로에서 이 코드를 거쳤다.

```text
애플리케이션의 파라미터 설정 · addBatch()
  → PreparedStatement 프록시
  → 로그용 SQL 문자열 생성
  → JDBC 드라이버
```

나는 호출이 드라이버와 DB 사이에서 기다리는 것으로 생각했다. 하지만 실제 실행 객체는 로깅 프록시였고, 먼저 살펴볼 곳은 그 내부 상태였다.

작은 입력이 아주 오래 걸린 뒤 완료되는 것도 확인했다. 완전히 멈춘 것이 아니라 극단적으로 느리게 진행하고 있었다. 따라서 이때 관측한 증상을 곧바로 데드락이나 무한 대기로 부르는 것도 맞지 않았다.

덤프는 내가 서버에서 확보했고, 라이브러리 바이트코드 분석과 실험 코드 작성에는 AI의 도움을 받았다. 나는 실험 범위와 조건을 정하고 배포·실행한 결과를 확인하면서 가설을 좁혔다.

## 같은 파라미터 위치에 값을 넣어도 로그용 목록은 계속 늘었다

분석한 프록시는 JDBC 실행용 파라미터와 별도로 로그용 값을 보관했다. 파라미터 인덱스에 덮어쓰는 대신 목록에 계속 추가했고, `addBatch()` 뒤에도 그 목록을 비우지 않았다.

```text
첫 행 설정 → 로그용 값 보관 → addBatch()
다음 행 설정 → 이전 값 뒤에 다시 추가 → addBatch()
다음 행 설정 → 더 길어진 목록을 바탕으로 로그 문자열 생성
```

DB에 보낼 batch 크기를 줄여도 이 목록은 남았다. 그래서 한 번에 전송하는 행 수만 조절해서는 해결되지 않았다. 반면 이 프록시의 `clearParameters()` 경로에서는 로그용 목록도 비웠다.

이 동작을 확인한 뒤 정상적으로 배치 적재를 하던 다른 코드를 다시 봤다. `addBatch()` 다음에 `clearParameters()`가 이미 있었다. 처음 비교할 때는 타임아웃 같은 설정에만 집중해 이 차이를 놓쳤다.

행별 `executeUpdate()`는 문제가 재현되는 batch 경로를 피하는 우회였다. 그 우회가 동작한다는 사실과 batch 경로가 느린 원인을 알아냈다는 것은 구분해야 했다.

## 행마다 상태를 비우고, 1,000건씩 전송했다

파라미터를 모두 바인딩한 뒤 `addBatch()`를 호출하고, 바로 `clearParameters()`로 현재 파라미터를 초기화했다. 전송은 1,000건 단위로 나눴다. 다음은 핵심 순서만 남긴 의사코드다.

```kotlin
for ((index, row) in rows.withIndex()) {
    bindAllParameters(ps, row)
    ps.addBatch()
    ps.clearParameters()

    if ((index + 1) % 1_000 == 0) {
        ps.executeBatch()
        ps.clearBatch()
    }
}
if (rows.size % 1_000 != 0) {
    ps.executeBatch()
}
```

`addBatch()`는 현재 파라미터 집합을 batch에 추가한다. `clearParameters()`는 현재 바인딩 값을, `clearBatch()`는 모아 둔 batch 명령을 비운다. 역할이 다르다. 다음 행에서는 모든 파라미터를 다시 바인딩했다. 이 조합에서 batch에 추가한 값이 유지되고 정상 적재되는지도 확인했다. [JDBC PreparedStatement 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/PreparedStatement.html)

라이브러리의 전역 설정을 바꾸는 대신 해당 Statement의 호출 순서를 바꿨다. 이 프록시에서 확인한 해결책이므로, 모든 JDBC batch 코드에 성능 개선용으로 같은 호출을 넣어야 한다는 뜻은 아니다.

전송 단위를 나눴지만 커밋은 마지막에 한 번만 했다. 기존 스냅샷 삭제와 새 데이터 적재를 같은 트랜잭션으로 묶고, 커밋 전에 적재 건수를 확인했다. 예외가 발생하면 명시적으로 롤백하도록 했다.

커넥션의 `use {}`만으로 롤백을 보장한다고 볼 수는 없다. `use`는 `close()`를 호출하고, JDBC는 활성 트랜잭션을 남긴 채 연결을 닫았을 때의 결과를 구현에 맡긴다. 직접 트랜잭션을 관리한 만큼 성공·실패 경로도 코드에 명시했다. [JDBC Connection 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/Connection.html#close())

## 전환 뒤에는 정기 실행 기록으로 확인했다

수정 후 비교한 것은 “끝났는가”와 “몇 초 걸렸는가”만이 아니었다. 입력에 맞는 행이 저장됐는지 먼저 확인하고, INSERT 구간과 전체 Job 시간을 나눠 봤다. 이후 정기 실행도 여러 번 확인했다.

| 전체 Job 시간 | 전환 전 | 전환 후 |
|---|---:|---:|
| 관측 횟수 | 9회 | 6회 |
| 중앙값 | 435초 | 약 94초 |
| 관측 범위 | 353~501초 | 91~101초 |

중앙값 기준으로 약 78% 줄었고 관측된 실행 시간의 편차도 작아졌다. 다만 같은 입력을 번갈아 실행한 실험은 아니다. 수십만 건 규모의 전환 전후 정기 실행 기록이며, 실행일별 입력량과 서버 부하가 완전히 같지는 않았다. 이 결과는 당시 운영 조건에서의 개선으로 해석했다.

최종 변경은 로그용 상태 초기화, batch 전송, 건수 검증과 롤백을 함께 포함한다. 표의 차이를 `clearParameters()` 한 줄의 독립적인 효과로 분리한 실험도 아니다.

처음 우회할 때는 적재가 끝나면 문제가 해결됐다고 생각했다. 다시 추적하면서 호출 이름보다 실행 중인 객체와 그 객체가 보관하는 상태를 봐야 한다는 것을 배웠다. 이전 글의 원인 설명을 고치는 이유도 여기에 있다.
