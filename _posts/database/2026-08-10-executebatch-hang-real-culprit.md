> 실무에서의 조사와 판단 과정을 중심으로 재구성했다. 실제 운영 구성·업무 규칙·실측 원문은 싣지 않았으며, 아래 흐름도와 코드는 원리를 설명하기 위한 예시다.

앞서 [트러블슈팅 글](/posts/oracle-executebatch-hang-debugging/)을 하나 발행했다. 대량 데이터를 DB에 적재하는 배치가 예외도 타임아웃도 없이 멈춘 것처럼 보였다. 당시 결론은 이랬다.

> IDENTITY 테이블에 executeBatch로 적재할 때만 멈춘다. 행별 `executeUpdate`로 바꾸니 정상 완료됐다.

그 결론이 틀렸다.

실제 원인은 IDENTITY나 `executeBatch` 자체가 아니었다. JDBC 호출을 감싸는 SQL 로깅 프록시였다. 행별 `executeUpdate`는 느려지는 호출 경로를 피했을 뿐, 그 경로가 왜 느린지는 설명하지 못했다.

이 글은 그 정정 기록이다.

## 1. 그때 그렇게 쓴 근거

당시 판단이 아무 근거 없이 나오지는 않았다. 나는 같은 환경에서 되는 코드와 안 되는 코드를 1:1로 대조해 이렇게 좁혔다.

```text
SELECT 1 통과
DELETE 통과
COMMIT 통과
INSERT executeBatch 구간에서 정지
```

커넥션은 빌린 직후 사용할 수 있었고, IDENTITY 채번도 행별 INSERT에서는 동작했다. 차이가 batch 호출 경로에 있다고 판단했다. 다만 이 관측만으로 이후의 락 대기나 드라이버 내부 문제까지 제외할 수는 없었다.

원글에도 단서는 달아뒀다. 항상 충돌한다는 뜻이 아니고 내부 메커니즘은 단정하지 않는다고 썼다. 그 신중함 자체는 틀리지 않았다.

틀린 것은 두 가지다. 첫째, 메커니즘도 모르면서 executeBatch라는 이름을 원인 자리에 놓았다. 둘째, 증상이 사라진 우회를 해결로 승격시켰다.

## 2. 우회 방식이 동작해 추가 분석을 멈췄다

원인 확인이 늦어진 이유는 우회 방식이 동작해 추적을 멈췄기 때문이다.

적재가 완료되고 행 수도 맞으니 당장의 문제는 사라졌다고 봤다. 다시 분석한 계기는 성능이었다. 행별 실행의 비용이 컸고, 처리량이 비슷한 실행 사이에서도 소요 시간 차이가 났다.

처리 건수만으로 시간을 설명할 수 없었다. 이때부터 완료 여부와 별개로 호출 구간별 비용을 비교했다.

## 3. 호출 경로를 비교한 뒤 스레드 덤프를 확인했다

재추적에서 세운 가설과 각각을 가른 실험이다.

| 가설 | 판별 실험 | 결과 |
|---|---|---|
| IDENTITY 채번이 원인 | 자동 채번 유무와 batch·행별 실행을 교차 비교 | 자동 채번 없는 테이블에서도 지연되어 단독 원인에서 제외 |
| executeBatch 자체가 원인 | 지연을 만드는 내부 동작을 설명할 수 있는지 확인 | API 이름만으로는 검증 가능한 가설이 되지 않음 |
| 큰 요청 크기가 원인 | batch에 한 행만 넣어도 같은 증상이 나는지 확인 | 큰 요청에서만 생기는 문제로 설명할 수 없었음 |
| queryTimeout 설정이 원인 | 정상 동작하던 코드와 설정을 비교하고 설정을 제거 | 지연이 남아 해당 설정만으로 설명할 수 없었음 |
| 이전 실행의 미커밋 작업이 원인 | 블로킹 세션을 확인하고 단일 실행으로 대조 | 해당 실험에서 지연을 설명할 락 대기를 찾지 못함 |

분석 중 `executeBatch` 자체가 원인이라는 설명을 접했을 때, 어느 구현의 어떤 동작이 느리다는 뜻인지 되물었다. 드라이버에 버그가 있을 수는 있지만, API 이름만으로는 가설을 검증할 수 없다.

스레드 덤프를 보자 JDBC 호출 도중 SQL 로깅 코드에서 시간을 쓰고 있었다. 실제 클래스명과 스택 원문 대신 호출 관계만 그리면 이렇다.

```text
애플리케이션의 addBatch() 호출
  → JDBC 프록시
  → 로그 메시지를 만드는 코드에서 지연
```

DB가 요청을 처리하느라 늦는다고 생각했는데, 먼저 확인할 곳은 그 호출을 감싼 프록시였다.

## 4. 설정 이름보다 실행 중인 객체를 확인한다

애플리케이션의 JDBC 호출과 드라이버 사이에는 로깅이나 계측을 위한 래퍼가 끼어 있을 수 있다.

```text
애플리케이션
  → PreparedStatement 래퍼·프록시
  → JDBC 드라이버
  → DB
```

나는 SQL 로그가 찍힌다는 사실만 보고 익숙한 계층에서 출력하는 것으로 생각했다. 실제로 어느 객체가 JDBC 호출을 받는지는 확인하지 않았다.

이후에는 의존성 선언뿐 아니라 실행 중인 Statement의 타입, 드라이버 설정, 실제 로딩된 라이브러리를 함께 확인했다. 설정을 읽는 것과 그 설정이 만드는 호출 경로를 이해하는 것은 달랐다.

## 5. 실행 파라미터와 로그용 상태의 수명이 달랐다

`javap`으로 분석해 보니 로그용 파라미터 목록이 다음 호출까지 남아 있었다. 라이브러리의 역컴파일 코드나 내부 구현은 옮기지 않고, 문제를 설명하는 데 필요한 동작만 정리한다.

```text
행의 파라미터 설정 → 실행용 값과 별도로 로그용 상태에 값이 쌓임
batch 경로        → 로그용 상태가 정리되지 않은 채 다음 행으로 진행
다음 행           → 이전 행의 값까지 포함해 로그 처리
명시적 초기화     → 다음 행으로 넘어갈 때 로그용 상태가 남지 않음
```

매 행의 값만 처리할 것으로 생각한 로깅 코드가 이전 행에서 남은 값까지 반복해서 다루고 있었다. 문자열을 만드는 비용도 함께 커졌다. DB로 전송할 행 수만 줄여서는 이 상태 누적을 해결할 수 없었다.

남은 의문은 행별 `executeUpdate`가 멀쩡했던 이유였다.

분석한 프록시는 두 호출 경로에서 로그용 상태를 정리하는 방식이 달랐다. 행별 실행 경로에서는 정리되던 상태가 batch 경로에는 남았다. 이 프록시에서 확인한 동작이고, JDBC 구현 전반의 성질로 볼 근거는 없다.

batch만 느리고 행별 실행은 완료되던 처음의 비대칭은 이 정리 방식의 차이 때문이었다. 현상은 봤지만 원인을 잘못 짚었다.

그때 배치는 완전히 멈춘 것이 아니라 아주 느리게 진행하고 있었다. 예외 없이 오래 걸린다는 이유만으로 I/O 대기라고 판단한 것도 잘못이었다.

## 6. 로그용 상태를 정리하고 batch 전송을 유지했다

다음 두 줄은 JDBC 호출 순서를 설명하기 위한 예시다. 매 행의 필요한 파라미터를 모두 바인딩한 뒤 실행한다.

```kotlin
ps.addBatch()
ps.clearParameters()   // 현재 파라미터를 비우고 다음 행에서 다시 바인딩
```

`addBatch()`는 현재 파라미터 집합을 batch에 추가하고, `clearParameters()`는 현재 바인딩 값을 지운다. batch 목록을 비우는 `clearBatch()`와는 다르다. 분석한 프록시에서는 이 호출이 로그용 상태도 정리했으므로, 전역 설정을 바꾸지 않고 해당 Statement의 동작을 수정할 수 있었다.

이 호출이 성능 문제를 푼 것은 이번 드라이버·프록시 조합에서였다. 다른 batch 코드에 쓰려면 실제 조합에서 batch에 추가한 값이 보존되는지 확인해야 하고, 어느 경우든 다음 행의 파라미터는 모두 다시 바인딩해야 한다. 나는 로그용 상태의 초기화와 전송 단위의 분할을 함께 적용하고 적재 결과를 대조했다.

원인을 규명한 뒤 되는 선례로 삼았던 다른 배치를 다시 열어봤다. 같은 한 줄이 이미 있었다.

처음에는 이 차이를 눈여겨보지 않았다. 파라미터 누적을 알고 나서야 왜 중요한지 이해했다. 선례를 볼 때 queryTimeout이라는 내 가설에 해당하는 설정만 비교했던 것이 문제였다.

어느 줄이 결정적인지는 원인을 알기 전에는 알 수 없다. 선례와 비교할 때는 차이를 전부 나열한 뒤 좁히는 편이 빠르다.

## 7. 완료 시간뿐 아니라 행 수와 구간별 비용을 비교했다

개선 후에는 전체 실행 시간이 줄었고, 반복 실행의 소요 시간 차이도 작아졌다. 다만 이 글에는 운영 건수·시간·로그 원문 대신 무엇을 비교했는지를 남긴다.

| 검증 항목 | 확인한 이유 |
|---|---|
| 적재 건수와 데이터 일치 | 누락된 데이터를 빠르게 처리한 것을 개선으로 오인하지 않기 위해 |
| INSERT 구간과 전체 Job 시간 | 쓰기 비용 감소와 전체 실행 결과를 분리하기 위해 |
| 같은 크기 구간의 처리 시간 | 뒤쪽 구간으로 갈수록 누적 비용이 다시 커지는지 보기 위해 |
| 반복 실행의 소요 시간 | 한 번 빨라진 결과만으로 결론 내리지 않기 위해 |

`N`개 행을 `B`개씩 보내면 애플리케이션의 `executeBatch()` 호출 수는 마지막 잔여 행을 포함해 `ceil(N / B)`다. 이것은 호출 수이고, 실제 DB 네트워크 왕복 횟수는 따로 재지 않았다.

구간별 시간에서도 뒤로 갈수록 지연이 커지던 현상이 해소된 것을 확인했다. 이 실행에서 본 결과라서 모든 입력 크기로 일반화하지는 않는다.

## 8. 실험은 이렇게 안전하게 짰다

실험이 실제 서비스 데이터에 영향을 주지 않아야 했다. 그래서 비교용 테이블과 실험 실행 범위를 분리하고, 속도보다 먼저 결과가 온전히 적재됐는지 확인했다.

- **비교용 테이블로 격리했다.** 읽기 대상과 쓰기 대상을 구분하고, 실험 후 정리할 대상을 명확히 했다.
- **쓰기 대상을 검사했다.** 의도한 실험 테이블이 아니면 실행하지 않도록 했다.
- **결과 행수를 검증했다.** 일부 입력만 처리하고도 성공하는 경우를 막기 위해 기대 건수와 실제 결과를 대조했다.
- **단일 실행 가드를 넣었다.** 2회차가 1회차의 미커밋 트랜잭션에 락 대기로 걸리면 로그상 hang과 구분이 안 돼 결론 자체가 오염된다.

리뷰에서는 실패 경로도 다시 확인했다. 직접 커넥션을 관리하는 코드에서 `use {}`가 보장하는 것은 `close()` 호출이지 명시적인 롤백이 아니다. JDBC 문서도 활성 트랜잭션이 있는 상태로 `close()`했을 때 결과를 구현에 맡긴다. 직접 관리하는 트랜잭션은 성공 시 커밋, 실패 시 롤백을 명확히 해야 한다. 전송 단위를 나누는 것과 커밋 단위를 나누는 것도 별개다.

## 9. 배운 것

1. **증상이 사라진 것과 원인을 아는 것은 다르다.** 우회가 동작한 뒤에도 원인을 확인하지 못했다는 사실은 남는다.
2. **hang이 의심되면 스레드 덤프를 먼저 확인한다.** 로그는 어디를 지나갔는지는 보여주지만, 현재 어느 호출에서 멈춰 있는지는 보여주지 못한다.
3. **멈춘 것과 느린 것을 구분한다.** 스레드 덤프를 시간 간격을 두고 비교하고, 처리 건수와 CPU 사용 등 진행 여부도 함께 확인한다. 같은 프레임이 반복된다고 모두 I/O 대기는 아니다.
4. **X 자체가 원인이라는 말은 라벨이지 가설이 아니다.** 메커니즘을 한 문장으로 대지 못하면 실험 설계도 못 한다.
5. **발행은 종결이 아니다.** 틀린 결론을 공개해두면 다른 사람도 같은 우회로 따라 들어온다. 정정할 의무가 남는다.
