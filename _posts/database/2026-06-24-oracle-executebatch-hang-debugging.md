> 실무에서의 조사 과정을 설명용 예제로 재구성했다. 실제 데이터 원천·운영 구성·스키마·측정 원문은 싣지 않았으며, 코드와 오류 흐름은 학습을 위한 예시다.

외부에서 읽은 데이터를 Oracle에 적재하는 작업이 **예외도, 타임아웃도 없이 멈춘 것처럼 보였다**. 네트워크·커넥션 풀·DB 락을 의심했고, 정상 동작하던 코드와 대조했다. 호출 경로의 차이는 찾았지만 원인 확인까지 이르지는 못했다.

## 미리 보는 결론

겹쳐 있던 증상은 다음 두 가지였다.

1. **ORA-02289 (시퀀스가 존재하지 않습니다)** - Exposed가 INSERT SQL에 존재하지 않는 시퀀스의 `NEXTVAL`을 넣었다.
2. **batch INSERT 구간 지연** - batch 호출에서는 장시간 진행 로그가 없었고, 행별 `executeUpdate`로 바꾸자 완료됐다. 후속 분석에서는 실제 지연 지점이 `addBatch()`를 감싼 로깅 코드임을 확인했다.

당시에는 정상 동작하던 코드와 비교해 다음 차이를 확인했다.

- ORM 경로와 직접 JDBC 경로의 차이
- 커넥션 borrow 직후 생존 확인
- 행별 `executeUpdate`
- 명시적 커밋

이 항목들이 모두 필요한 해결책이었다는 뜻은 아니다. 행별 실행이 완료된 것은 관측이고, batch 경로의 내부 원인을 설명하는 것은 별개의 작업이었다.

## 1. 증상 - 에러 없이 멈춘다

적재 배치를 수동 트리거하면 장시간 응답이 돌아오지 않았다. 로그는 적재 시작 지점에서 멈추고, 대상 테이블에는 행이 들어가지 않았다. `setQueryTimeout`을 명시해도 스레드는 풀리지 않았다.

단계 로그를 쪼개 보니 멈추는 위치가 보였다.

```text
SELECT 1 통과
DELETE 통과
COMMIT 통과
INSERT executeBatch 구간에서 정지
```

처음에는 커넥션이나 소켓의 타임아웃을 의심했으나 커넥션을 빌린 시점부터 죽어 있던 것은 아니었다.

앞의 `SELECT 1`, `DELETE`, `COMMIT`은 통과했기 때문이다. 다만 batch INSERT를 묶어 찍은 로그만으로는 `addBatch()`에서 느린지, 전송 이후에 느린지 구분할 수 없었다.

## 2. 초기 가설과 당시 관측의 한계

처음에는 환경 문제처럼 보였다. 정상 동작하던 적재 코드와 대조하면서 가설을 검토했다. 후속 분석을 기준으로 보면, 아래 관측 중 일부는 완전한 반증이 아니라 다음 조사 대상을 고르는 단서였다.

| 가설 | 관측과 판단 범위 |
|---|---|
| 네트워크나 소켓이 대량 패킷을 차단한다 | 다른 적재 코드는 완료됐다. 호출 방식과 요청 크기까지 같다는 뜻은 아니므로 추가 대조 필요 |
| 테이블 락이나 이전 트랜잭션이 있다 | `DELETE`가 통과했다. 이후 INSERT의 락 대기까지 배제하지는 못하므로 블로킹 세션 확인 필요 |
| 풀에서 처음부터 죽은 소켓을 빌렸다 | 생존 확인 쿼리가 성공했으므로 적어도 빌린 직후에는 사용 가능했음 |
| ORM batchInsert의 generated keys 요청이 문제다 | 라이브러리 소스 확인 결과 해당 경로는 `NO_GENERATED_KEYS`로 실행됨 |
| IDENTITY 컬럼 자동 채번 자체가 문제다 | 같은 IDENTITY 테이블에 행별 `executeUpdate`로 넣으면 정상 완료됨 |

되는 코드와 안 되는 코드를 대조하는 것은 유용했다. 다만 **완료됐다는 차이와 원인이 밝혀졌다는 결론을 구분해야 했다.**

## 3. 조회 쪽 문제를 먼저 걷어냈다

처음부터 적재 단계까지 도달한 것은 아니었다. 앞단의 조회가 실패했을 때는 쿼리를 먼저 의심했다.

- 파티션 조건 바인딩 방식 문제인가?
- 드라이버가 바인드 변수를 기대대로 처리하지 못하나?
- CTE(`WITH` 절)가 실행 계획이나 드라이버와 맞지 않나?

각 가설에 맞춰 쿼리를 수정했지만 증상은 해소되지 않았다. 결국 JOIN·윈도우·집계를 제거하고 소수 행만 읽는 단순 조회로 줄였다. 이 쿼리에서도 실패했으므로, 복잡한 집계 로직보다 연결 대상과 접근 조건을 먼저 확인했다.

원격 환경에서 확인해야 할 때는 한 번의 실험으로 무엇을 구분할지 먼저 정하는 편이 좋았다. 큰 수정 대신 **작은 조회와 단계 로그**를 넣으면 실패 지점을 분리하기 쉬웠다.

## 4. 쿼리와 연결 대상을 분리해서 본다

단순 조회에서 연결 대상과 데이터 위치의 불일치를 가리키는 오류가 드러났다. 실제 엔드포인트나 오류 원문 대신 조사 순서를 정리하면 다음과 같다.

```text
집계 쿼리 실패
  → 최소 조회로 축소
  → 연결 대상과 데이터 위치 대조
  → 연결 대상 수정 후 원래 쿼리로 재검증
```

오류가 발생하는 단계가 달라졌다는 사실만으로 원인을 확정할 수는 없다. 오류 내용과 설정을 대조하고, 수정 후 같은 쿼리가 통과하는지까지 확인해야 한다.

조회가 통과한 뒤에도 적재 지연은 남았다. 앞단의 실패와 뒷단의 지연은 별개였다. 여기서 얻은 교훈은 다음과 같다.

> 오류 메시지의 내용만 보지 말고, 오류가 발생한 단계가 어떻게 바뀌었는지를 본다. 단계가 바뀌면 원인 후보도 바뀐다.

## 5. 조회·변환·적재를 나눠 관측한다

조회 다음에는 변환 단계의 오류도 분리했다. 예를 들어 숫자 변환이 실패한다면 입력 형식과 처리 기준을 확인해야 한다. 이 문제를 바로잡았다고 적재 단계의 지연까지 해결된 것은 아니다.

변환까지 통과한 뒤에는 적재 단계의 진행 여부를 관측했다.

타임아웃으로 예외를 만들려는 시도는 실패했다.

- `queryTimeout`을 짧게 설정해도 스레드가 풀리지 않음
- 커넥션 레벨 타임아웃을 시도해도 기대한 진단 로그가 남지 않음

그래서 전략을 바꿨다. 예외를 강제로 만들기보다, **어디까지 실행됐는지 관측**하는 방식으로 접근했다.

먼저 큰 단계별로 로그를 넣었다. 커넥션 획득 -> DELETE -> batch INSERT 순으로 수행되던 로직의 각 단계 직전과 직후에 로그를 심었다.

```text
STEP 1: 커넥션 획득 전
STEP 2: 커넥션 획득 후
STEP 3: DELETE 전
STEP 4: DELETE 후
STEP 5: batch INSERT 전
STEP 6: batch INSERT 후
```

batch INSERT를 감싸던 `catch`가 실행되지 않는다는 사실도 단서였다. 하지만 예외가 없다는 사실만으로 I/O 대기라고 판단할 수는 없었다. CPU를 쓰며 아주 느리게 진행하는 경우에도 예외가 없을 수 있다.

이후 단계 로그를 더 쪼갔다.

- 커넥션 획득 전후를 나누니 획득 후 로그는 찍힘 → 커넥션 획득 hang 가능성 낮음
- `DELETE`와 batch INSERT를 나누니 `DELETE`는 통과 → 이후 단계의 지연을 별도로 확인
- 첫 청크 완료 로그도 찍히지 않음 → 청크 안의 바인딩·`addBatch()`·`executeBatch()`를 추가로 분리할 필요

당시에는 이를 응답 없는 I/O 대기로 해석했다. **후속 분석에서 이 판단이 틀렸음을 확인했다.** 단계 로그는 구간을 알려주지만, 현재 스레드가 어디에서 시간을 쓰는지는 덤프와 함께 봐야 했다.

## 6. ORA-02289와 executeBatch hang

마지막에는 시퀀스·커넥션·트랜잭션·batch 호출 방식을 하나씩 분리했다.

Exposed가 만든 INSERT에 존재하지 않는 시퀀스의 `NEXTVAL`이 들어가 `ORA-02289`가 발생하는 문제를 확인했다. 매핑을 수정해도 적재 지연은 남았다. 즉 자동 PK 문제와 적재 지연은 분리해서 다뤄야 했다.

남은 차이는 batch 호출 방식이었다.

아래는 두 실행 방식을 비교하기 위한 의사코드이며, 바인딩 함수와 트랜잭션 처리는 생략했다.

```kotlin
// batch 방식: 여러 행의 파라미터 집합을 추가한 뒤 실행
for (row in rows) {
    ps.setValues(row)
    ps.addBatch()
}
ps.executeBatch()

// 행별 방식: 각 행을 바로 실행
for (row in rows) {
    ps.setValues(row)
    ps.executeUpdate()
}
```

`addBatch/executeBatch`를 행별 `executeUpdate`로 바꾸자 적재가 완료됐고, 대상 테이블의 행 수도 기대와 맞았다.

정리하면, **batch 경로를 행별 실행으로 바꾸자 완료됐다.** 당시 확정할 수 있던 것은 다음 관측까지였고, 내부 원인은 아직 몰랐다.

- 커넥션 borrow 자체는 성공했다.
- `DELETE`와 `COMMIT`은 통과했다.
- IDENTITY 채번 자체는 행별 INSERT에서 정상 동작했다.
- batch 호출 경로에서만 긴 지연이 재현됐다.

## 7. 원리 정리

### 7.1 ORA-02289 - ORM 자동 PK가 DB와 어긋날 때

Exposed의 `LongIdTable` 계열 자동 증가 id는 Oracle에서 시퀀스 기반 전략을 사용할 수 있다. 해당 버전에서는 명시 시퀀스가 없을 때 fallback 시퀀스명의 `NEXTVAL`을 INSERT SQL에 넣는 경로가 있었다.

설명용 DDL을 IDENTITY 방식으로 두면 차이가 드러난다.

```sql
ID NUMBER GENERATED ALWAYS AS IDENTITY
```

Oracle IDENTITY는 내부적으로 시퀀스를 사용하지만, ORM이 추정한 이름의 시퀀스가 별도로 존재한다는 뜻은 아니다. INSERT가 존재하지 않거나 접근할 수 없는 시퀀스를 참조하면 `ORA-02289`가 발생할 수 있다.

해결은 ORM이 id 컬럼을 INSERT 컬럼 목록에서 제외하게 만드는 것이다.

다음은 공개 Exposed API로 작성한 매핑 예시다. 테이블 생성용 전체 DDL이 아니라, DB에서 생성하는 컬럼을 INSERT에서 생략하도록 지정하는 부분이다.

```kotlin
object ExampleRecords : IdTable<Long>("example_record") {
    override val id = long("id").databaseGenerated().entityId()
    override val primaryKey = PrimaryKey(id)
    val payload = text("payload")
}
```

이렇게 하면 id 값은 DB의 IDENTITY가 채운다. DDL을 바꾸지 않고 ORM 매핑만 DB의 PK 생성 방식에 맞춘다.

교훈은 단순하다. **ORM의 자동 PK 전략은 DB의 실제 PK 생성 방식과 정확히 맞아야 한다.** 문제가 생기면 ORM 설정만 보지 말고 실제 생성된 INSERT SQL을 확인해야 한다.

### 7.2 executeBatch hang과 queryTimeout의 한계

`setQueryTimeout`은 만능 타임아웃이 아니다. Oracle JDBC 문서에 따르면 `Statement.setQueryTimeout`은 내부적으로 `Statement.cancel`에 의존한다. 그런데 `cancel`은 네트워크와 DB가 정상적으로 응답한다는 전제가 있어야 동작한다. 네트워크가 끊겼거나 DB 서버가 hung 상태인데 JDBC가 `IOException`도 받지 못하는 경우에는, timeout이 실행 스레드를 풀어주지 못할 수 있다.

이런 종류의 무한 read를 줄이려면 statement timeout만으로는 부족하다. 운영 중인 드라이버와 풀 설정에서 지원하는 socket read timeout을 명시적으로 검토해야 한다.

- `oracle.jdbc.ReadTimeout` 연결 프로퍼티
- 환경에 따라 `oracle.net.READ_TIMEOUT`
- 커넥션 풀의 validation / maxLifetime / idleTimeout
- 필요 시 Oracle Net keepalive 또는 DCD 설정

다만 이 글의 지연 원인은 후속 분석에서 로깅 프록시로 밝혀졌다. 위 항목은 네트워크 대기 진단에 관한 일반적인 참고 사항이지, 이번 원인을 해결한 설정 목록이 아니다. DB 실행 이전의 로깅 코드가 느리다면 쿼리 타임아웃만으로 해결되지 않을 수 있다.

### 7.3 행별 executeUpdate의 trade-off

행별 `executeUpdate`는 batch보다 느릴 수 있다. 대신 다음 장점이 있었다.

- 첫 행부터 성공/실패 위치를 관측하기 쉽다.
- batch 드라이버 경로를 피할 수 있다.
- 청크 커밋과 조합하면 장시간 트랜잭션을 피할 수 있다.

반대로 청크 커밋은 적재 중 실패 시 캐시 테이블이 부분 상태가 될 수 있다. 이 경우에는 적재 완료 플래그, 기준일 가드, 재실행 정책 같은 운영 안전장치가 필요하다. 원자성이 더 중요하면 끝에서 한 번만 커밋하고, undo/redo 부담을 감수하는 쪽이 맞을 수 있다.

## 8. 재사용할 디버깅 방법론

1. **되는 선례를 먼저 찾아 1:1로 대조한다.** 같은 환경에서 되는 코드가 있으면 환경 전체보다 그 차이가 더 강한 단서다.
2. **추측을 코드와 소스로 검증한다.** ORM이 만드는 SQL, JDBC 호출 옵션, generated keys 사용 여부는 소스와 로그로 확인할 수 있다.
3. **변수를 하나씩 제거한다.** batch와 행별 실행의 차이는 조사할 호출 경로를 찾는 단서였다. 그 자체가 원인 규명은 아니었다.
4. **관측 가능한 비대칭을 본다.** 조회는 통과하지만 적재만 멈춤, `DELETE`는 통과하지만 batch INSERT만 멈춤, 예외는 없지만 로그도 진행되지 않음 같은 비대칭이 가설을 줄인다.
5. **hang은 예외와 다르게 다룬다.** try-catch와 queryTimeout만 믿지 말고, 단계 로그로 어디까지 갔는지를 먼저 확보한다.
6. **원격 실험은 작게 만든다.** 최소 조회, 단계 로그, batch 크기 축소처럼 한 번의 실행으로 무엇을 구분할지 정한다.

## 정리

이번 문제는 하나의 원인으로 깔끔하게 설명되지 않았다.

- 조회 실패는 데이터 엔드포인트 불일치였다.
- 변환 단계의 오류는 입력 형식과 처리 기준을 별도로 확인해야 했다.
- `ORA-02289`는 Exposed 자동 PK 전략과 Oracle IDENTITY DDL의 불일치였다.
- 적재 지연은 batch 호출 경로에서 재현됐고, 행별 `executeUpdate`로 우회했다.

> ⚠️ **우회 성공을 원인 규명으로 읽으면 안 됩니다.** 후속 분석에서 원인은 SQL 로깅 프록시의 상태 누적으로 밝혀졌습니다. 자세한 내용은 [executeBatch가 멈춘 원인은 SQL 로깅 라이브러리였다](/posts/executebatch-hang-real-culprit/)를 참고하세요.

가장 중요한 교훈은 **환경을 의심하기 전에 같은 환경에서 되는 선례와 1:1로 대조하는 것**이다. 그리고 hang처럼 예외가 없는 문제는, 예외 처리보다 단계 관측이 먼저다.
