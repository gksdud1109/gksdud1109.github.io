운영 정산 최종 리포트와 내부 데이터가 맞지 않는다는 제보를 조사했다. 비교 기준을 맞춘 결과, 이미 지급된 건의 계산식은 맞았지만 특정 날짜의 배치 실패로 원천 주문 일부가 집계되지 않았음을 확인했다.

기존 배치는 하루치 리포트를 한 번만 조회해 실패한 날짜를 다음 실행에서 다시 처리할 수 없었다. 주문이나 취소가 늦게 들어오는 경우도 놓쳤다. 이를 최근 7일 재조회와 차액 반영 방식으로 바꾸고, 재실행과 실패 복구 시나리오를 테스트로 검증했다.

## 1. 최근 7일을 다시 조회한다

기존 배치는 실행일 기준 전날 하루만 조회했다.

```text
1월 19일: 주문 API 성공 → report_log 저장
          취소 API 실패 → Job FAILED → 이후 step 미실행
다음 날  : 전날 하루만 조회 → 1월 19일을 다시 볼 경로 없음
```

Job이 `FAILED`로 끝나는 것 자체는 올바른 장애 표현이다. 문제는 그다음이다. 실패한 날짜를 이후 실행이 다시 수집하지 않으면 자동 복구가 없다. API에 주문이나 취소가 늦게 나타나는 경우도 똑같이 놓친다.

그래서 조회 범위를 전날 하루에서 최근 7일로 넓혔다.
7일 안에 생긴 일시적 실패나 늦게 도착한 변경은 다음 실행에서 다시 반영된다.

여기서 진짜 문제는 재조회의 멱등성이었다. 같은 주문을 매일 다시 수집해도 원장이 중복되면 안 된다. 동일 식별키를 다시 저장하면 기존 active 행을 삭제 상태로 내리고 최신 한 건만 active로 남기는 revision 방식으로 풀었다.

```kotlin
// 같은 식별키 재수집: 기존 active는 D로 내리고 최신 1건만 A로
findActive(report.key)?.markDeleted()
insert(report.asActive())
```

최종 상태는 멱등이고 물리 이력은 보존된다. 이 불변식은 실제 MySQL Testcontainers 통합 테스트로 확인했다.

범위는 정직하게 그었다. 7일을 넘는 누락은 자동 복구가 아니라 수동 backfill 대상이다. 자동 복구가 모든 과거를 책임지는 척하지 않기로 했다.

## 2. delta upsert로 매일 다시 맞춘다

같은 주문을 다시 조회해도 안전하려면 지급 계산 자체가 멱등해야 한다. 이 원리는 지난 글 [뒤늦게 들어온 취소까지 반영하는 배치 설계](/posts/existence-is-not-idempotency/)에서 따로 다뤘다. 요약하면, 존재 여부로 이미 처리했다고 판단하면 늦게 온 취소를 놓치므로, 원천 데이터로 현재의 기대 상태를 계산하고 기존 원장과의 차이만 반영한다.

```kotlin
val delta = expected - existing            // 부수효과는 차이만
if (delta != 0) { upsert(key, expected); ledger.adjust(delta) }
// 같은 걸 다시 수집해도 expected == existing이면 delta 0 → no-op
```

최근 데이터를 다시 수집해도 차이가 0이면 원장은 바뀌지 않는다. 늦게 도착한 취소가 들어오면 기존 금액과의 차이만큼만 차감된다. 이 차액 반영 방식이 재조회에 따른 중복 지급을 막는다.

## 3. 단위 테스트부터 Job E2E까지 검증한다

테스트가 하나도 없는 상태에서 시작했다. 정산처럼 조용히 새는 로직은 눈으로 지킬 수 없어서, 먼저 실제 MySQL을 띄우는 통합 테스트 베이스부터 만들었다.

```kotlin
abstract class DbTest {
    companion object { val db = MySQLContainer("mysql:8").apply { start() } }
    fun <T> tx(block: () -> T) = transaction(db) { block() }
}
```

도입하면서 한 번 크게 넘어졌다. 테스트를 혼자 돌리면 통과하는데 전체 스위트로 돌리면 순서에 따라 실패했다. Exposed가 전역 기본 DB를 공유해서, 앞 테스트가 연 연결이 뒤 테스트로 새어 든 것이다. 각 테스트를 자기 연결에 명시로 묶어(pin) 격리하자 사라졌다. 통합 테스트 하네스는 전역 가변 상태에 기대면 안 된다는 걸 여기서 배웠다.

그 위에 세 층을 쌓았다. 기준은 각 층이 무엇을 볼 수 있고 무엇을 볼 수 없는지였다.

| 층 | 무엇을 검증하는지 | 도구 |
|---|---|---|
| 단위 | 정책 경계값(반올림, 시행일 전후) | 순수 함수, DB·시계 없이 밀리초 |
| 서비스 통합 | 원장 흐름: 재계산, 차액 반영, 멱등, 다일자 | 실제 MySQL Testcontainers |
| Job E2E | 배선·전파·복구: 실패가 Job으로 전파되는지, 복구가 완주하는지 | Spring Batch 실행계층 + Testcontainers |

계산은 아래층에서, 배선과 전파와 복구는 위층에서 검증했다. 같은 경계값을 E2E에서 또 재는 건 새 정보가 없어 하지 않았다. 반대로 실패가 성공 상태로 숨는지는 프로세스를 직접 만들어서는 볼 수 없다. Spring Batch 실행계층을 타야만 드러나서 Job E2E가 따로 필요했다.

구현 전에 실패하는 테스트부터 작성했다. 한 번은 테스트 데이터가 계산 상수의 배수여서 반올림 오류가 드러나지 않았다. 경계값을 포함한 데이터를 사용해야 기존 구현의 문제를 정확히 재현할 수 있었다.

새 테스트가 통과하면 구현을 의도적으로 이전 상태로 되돌려 실제로 실패하는지 확인했다.

```kotlin
val delta = expected   // 일부러 깸: 차이가 아니라 기대값 → 이중 집계가 나야 테스트가 잡는다
```

집계 step에서 예외를 삼키던 skip 정책을 되살렸을 때 write 0건인데 상태만 `COMPLETED`가 되는 문제가 재현되어야, 해당 테스트가 실패 전파를 실제로 검증한다고 볼 수 있다.

한 번은 이전 구현으로 되돌려도 결과가 계속 통과로 표시됐다. 캐시를 비우고 다시 실행한 뒤 확인해 보니, 결과를 읽는 스크립트가 실패를 통과로 잘못 해석하고 있었다. 테스트뿐 아니라 결과를 수집하는 도구도 함께 검증해야 했다.

값이 실제로 바뀌는지 검증하려면 변경 전 상태를 먼저 명시해야 한다.

```kotlin
assertNull(findSummary(key))              // 복구 전
runRecovery()
assertEquals(expected, findSummary(key))  // 복구 후
```

이렇게 하지 않으면 신규 생성이 우연히 같은 최종값을 만들어 갱신인 척 통과한다.

## 마무리

정산 누락 건을 한 번 복구하는 데서 끝내지 않고, 최근 7일 재조회와 차액 반영으로 다음 실행에서 복구할 수 있게 했다. 여기에 단위·통합·Job E2E 테스트를 추가해 재실행, 실패 전파, 복구 동작을 확인했다.
