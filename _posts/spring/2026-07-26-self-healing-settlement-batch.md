> 실무 배치의 코드와 당시 조사 기록을 바탕으로 작성했다. 업무 식별자는 일반화했고, 날짜 예시는 설명용이다. 7일은 이때 구현한 재수집 범위다.

[앞선 글](/posts/existence-is-not-idempotency/)에서는 수집한 주문·취소를 올바르게 계산하고, 같은 데이터를 다시 처리해도 적립이 반복되지 않도록 바꿨다. 그런데 계산 로직을 고쳐도 해결되지 않는 누락이 남아 있었다. 주문 리포트는 DB에 있는데 적립과 집계가 만들어지지 않은 경우였다.

과거 실행 기록을 따라가 보니 주문 수집은 성공했지만, 이어지는 취소 API 호출이 HTTP 500으로 실패한 날이 있었다. 그 뒤의 적립·집계 Step은 실행되지 않았다. 문제는 다음 날 배치가 성공해도 이 데이터가 다시 처리되지 않는다는 점이었다.

## 주문 수집은 커밋됐고, 집계까지는 가지 못했다

당시 Job의 큰 흐름은 다음과 같았다.

```text
주문 리포트 수집 → 취소 리포트 수집 → 적립 계산 → 주문 집계
```

Job 전체가 하나의 트랜잭션은 아니었다. 주문 수집 Step이 끝나면 그 기록은 DB에 남았고, 이후 취소 수집이 실패해도 앞서 커밋한 주문 기록까지 사라지지 않았다.

여기에 두 가지 날짜 기준이 겹쳤다. 외부 API는 전날 하루를 조회했고, 후속 계산은 오늘 적재된 기록에서 처리할 주문을 골랐다.

```text
3일 실행
  2일 주문 수집 성공 → 3일 적재 시각으로 저장
  2일 취소 수집 실패 → Job FAILED
  적립·집계 미실행

4일 실행
  3일 리포트만 수집
  4일에 적재된 주문만 후속 계산 대상으로 선택
  → 3일에 저장해 둔 2일 주문은 대상에서 빠짐
```

원천 기록이 있으니 언젠가 처리되겠다고 생각하기 쉽지만, 실제 대상 조회 조건에는 들어오지 않았다. 실패했던 Job을 별도로 재시작하거나 과거 날짜를 지정하지 않는 한, 매일 새로 시작하는 배치만으로는 복구되지 않는 경로였다.

## 왜 최근 7일을 다시 가져오기로 했나

해결할 문제는 오래전 주문의 취소를 모두 찾는 것이 아니라, **수집이나 후속 처리에 실패한 최근 발생일을 다시 계산 대상으로 올리는 것**이었다.

그래서 전날 하루 대신 실행일 기준 D−7일부터 D−1일까지 조회하도록 바꿨다. 앞의 예시에서 4일 실행은 2일 리포트도 다시 가져온다. 취소 API가 복구돼 있다면 주문·취소를 함께 확보하고 후속 계산까지 진행할 수 있다.

7일이 API 지연의 최대치라는 근거가 있었던 것은 아니다. 당시 일별 수집량이 작아 최근 며칠을 반복 조회하는 비용을 감당할 수 있었고, 일시적 실패를 다음 정기 실행에서 되돌릴 수 있는 범위를 먼저 정한 것이다. 호출량과 보관 이력이 늘어나는 대신 복구 기회를 확보하는 선택이었다.

따라서 7일보다 오래된 누락까지 자동으로 해결되지는 않는다. 조사 과정에서 찾은 과거 장애 기록은 이 구조가 필요한 근거였지만, 새로 만든 7일 조회 범위 밖의 과거 데이터를 운영에서 모두 복구했다는 뜻은 아니다. 그 데이터는 날짜를 지정한 별도 재수집과 결과 확인이 필요하다.

## 다시 수집한 기록이 후속 처리까지 이어져야 했다

조회 기간만 넓히고 기존 저장 코드를 그대로 두면 충분하지 않았다. 같은 원천 키가 이미 있다는 이유로 저장을 건너뛰면 적재 시각이 예전 그대로 남고, 후속 계산은 다시 그 주문을 놓칠 수 있었다.

기존 수집 이력을 보존하되, 재수집한 기록을 새 revision으로 저장하고 이전 revision을 비활성화했다. 계산에는 현재 유효한 버전만 사용한다.

```text
같은 원천 키를 재수집
  → 이전 revision은 이력으로 보존
  → 새 revision을 현재 적재 시각으로 저장
  → 오늘 처리할 주문에 다시 포함
  → 유효한 원천 기록으로 적립·집계 재계산
```

원천 값이 같아도 새 revision을 저장하는 이유가 여기에 있었다. 당시 구조에서는 재적재가 미완료 후속 처리를 다시 시작하게 만드는 역할도 했다. 변경 없는 데이터 저장을 줄이려면, 먼저 적재 시각과 별개로 미처리 대상을 추적하는 경로가 필요했다.

이 방식은 수집 이력의 물리적인 행 수를 늘린다. 여기서 멱등성을 확인한 대상은 행 수가 아니라 최종 적립 상태와 추가 지급액이었다. 적립액은 원천을 재계산한 기대값과 저장값의 차이만 반영하므로, 같은 입력이면 추가 지급이 0이 된다.

페이지네이션도 함께 확인했다. 날짜를 넓혀도 각 날짜의 첫 페이지만 가져오면 그 뒤의 데이터는 계속 빠진다. 페이지를 순회해 수집하도록 바꿨고, 당시 작은 데이터량에 맞춰 수집 결과를 메모리에 모아 Reader에 넘겼다. 데이터량이 커지면 이 부분은 스트리밍이나 별도 Reader로 다시 검토할 지점이다.

## 계산 실패를 skip하면 재수집만으로는 고쳐지지 않는다

재수집은 다시 처리할 기회를 줄 뿐이다. 적립이나 집계에서 같은 오류를 계속 건너뛰면 다음 날에도 누락은 반복된다.

그래서 이번에 수정한 적립·집계 Step에서는 폭넓은 예외 skip을 제거했다. 금액 계산이나 저장에 실패하면 Job이 실패해야 조사와 재실행으로 이어질 수 있었다. 별도 지급 경로까지 모든 skip 정책을 일괄 변경한 작업은 아니었다.

복구 흐름은 결국 세 부분이 맞물려야 했다.

| 부분 | 맡은 역할 |
|---|---|
| 최근 7일 재수집 | 실패한 날짜를 다시 읽을 기회 확보 |
| 유효 revision과 차액 반영 | 다시 읽어도 현재 상태만 계산하고 중복 지급 방지 |
| 적립·집계 실패 전파 | 처리하지 못한 데이터를 성공으로 숨기지 않음 |

## 서비스 테스트와 Job 실행 테스트를 나눴다

실제 MySQL을 사용하는 Testcontainers 환경에서 적재 시각과 원천 기록을 바꿔 가며 검증했다. 서비스 테스트는 다른 날의 입력을 세밀하게 만들기 좋았고, Job 테스트는 Step 연결과 최종 실행 상태를 확인하는 데 필요했다.

| 검증 | 확인한 내용 |
|---|---|
| 다음 날 재적재를 재현한 서비스·저장소 통합 테스트 | 이전에 원천만 있던 주문을 다시 적재하면 누락 집계가 생성됨 |
| 취소 API 실패를 주입한 Job 테스트 | 주문 수집은 남고, Job은 FAILED이며 적립·집계는 실행되지 않음 |
| API가 복구된 뒤 Job을 다시 실행하는 테스트 | 수집부터 적립·집계까지 완료됨 |
| 집계에서 예외를 발생시키는 Job 테스트 | 오류를 건너뛰지 않고 Job이 FAILED로 끝남 |
| 동일 입력 재실행 테스트 | 적립 상태는 같고 추가 지급은 없음 |

Job 복구 테스트는 같은 기준일에서 실패 후 재실행했다. 다음 날로 적재 시각을 넘기는 복구는 별도의 서비스·저장소 통합 테스트로 확인했다. 두 검증을 합쳐 복구 경로를 확인했지만, 스케줄러가 실제 다음 날 동작하는 전 과정을 하나의 E2E로 검증한 것은 아니다.

테스트를 만들 때는 결과만 맞추지 않도록 변경 전 상태도 확인했다. 집계가 없던 주문에 집계가 생기는지, 기존 적립을 그대로 둬야 하는 재실행에서 추가 기록이 없는지를 각각 검사했다. 차액 계산이나 실패 전파를 의도적으로 이전 방식으로 되돌렸을 때 테스트가 실패하는지도 수동으로 확인했다.

이번 수정에서 중요했던 것은 조회 기간의 숫자보다, 실패한 데이터가 어디에서 다시 처리 대상에 들어오는지였다. 최근 데이터를 반복해서 가져오고, 현재 버전만 계산하고, 이미 반영한 금액과의 차이만 적용하는 흐름을 연결한 뒤에야 후속 실행을 복구 경로로 사용할 수 있었다.
