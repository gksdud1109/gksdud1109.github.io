> 실무에서 배운 복구 설계와 테스트 경험을 설명용 모델로 재구성했다. 날짜·조회 기간·코드는 예시이며, 실제 장애 내역이나 운영 정책을 나타내지 않는다.

정산 결과가 맞지 않을 때 처음부터 계산식만 의심하면 입력 누락을 놓칠 수 있다. 나는 비교 기준을 맞춘 뒤, 원천 수집·집계·원장 반영을 나눠 확인하면서 이 차이를 배웠다. 계산이 맞더라도 원천 기록을 빠뜨리면 최종 결과는 맞지 않는다.

그다음에는 빠진 데이터를 한 번 채우는 것으로 끝나는지 따져 봤다. 다음 실행에서도 놓친 날짜를 다시 읽지 않는다면 같은 문제가 반복될 수 있다. 재조회 범위를 겹치고 기대 상태와의 차액만 반영하는 방법, 그리고 이를 검증하면서 겪은 시행착오를 정리한다.

## 1. 최근 7일을 다시 조회한다

전날 하루만 조회하는 배치를 예로 들면 복구 공백이 드러난다.

```text
실행 A: 이전 날짜의 주문 수집 성공
        취소 수집 실패 → Job FAILED → 이후 Step 미실행
실행 B: 조회 날짜가 앞으로 이동 → A에서 실패한 날짜는 조회하지 않음
```

Job이 `FAILED`로 끝나는 것 자체는 올바른 장애 표현이다. 문제는 그다음이다. 실패한 날짜를 이후 실행이 다시 수집하지 않으면 자동 복구가 없다. API에 주문이나 취소가 늦게 나타나는 경우도 똑같이 놓친다.

해결 방향은 조회 범위를 겹치는 것이다. 여기서는 최근 7일을 재조회하는 예로 설명한다. 재조회 범위에 들어오는 일시적 실패나 늦게 도착한 변경은 후속 실행이 성공하면 다시 반영할 수 있다.

기간을 7일로 잡을지는 원천 API의 조회 가능 기간, 변경 데이터가 늦게 도착하는 정도, 재수집 비용을 보고 정한다. 재조회 구간과 원천 데이터의 날짜 기준이 맞는지도 함께 확인한다.

다음 문제는 같은 입력을 반복 수집했을 때 어떤 기록을 계산에 사용할지였다. 최신 상태와 이전 수집 이력을 구분하는 revision 방식을 검토했다. 설명용 모델로 나타내면 다음과 같다.

```text
같은 식별키를 다시 수집
  → 이전 버전 보존
  → 현재 계산에 사용할 버전 갱신
  → 해당 키의 기대 상태 재계산
```

이때 멱등하다는 것은 재실행 후의 계산 상태와 추가 반영액을 말한다. 수집 이력을 매번 남긴다면 물리적인 행 수까지 같을 필요는 없다. 현재 버전이 하나로 정해지는지와 재실행 후 추가 반영이 없는지를 MySQL Testcontainers 통합 테스트로 구분해 확인했다.

재조회 기간을 벗어난 누락은 별도의 backfill 대상이다. 정기 실행이 복구하는 범위와 과거 데이터를 다시 처리하는 경로는 따로 둔다.

## 2. delta upsert로 매일 다시 맞춘다

같은 주문을 다시 조회해도 안전하려면 지급 계산 자체가 멱등해야 한다. 이 원리는 지난 글 [뒤늦게 들어온 취소까지 반영하는 배치 설계](/posts/existence-is-not-idempotency/)에서 따로 다뤘다. 요약하면, 존재 여부로 이미 처리했다고 판단하면 늦게 온 취소를 놓치므로, 원천 데이터로 현재의 기대 상태를 계산하고 기존 원장과의 차이만 반영한다.

```text
기대액 = 현재 유효한 원천 기록으로 계산
차액 = 기대액 - 저장된 금액
차액이 0이 아니면:
  현재 상태를 기대액으로 갱신
  원장에 차액 기록
```

최근 데이터를 다시 수집해도 차이가 0이면 추가 반영은 없다. 늦게 도착한 취소는 기존 금액과의 차이만큼 차감한다. 이 설명은 같은 키의 처리가 직렬화되고 상태 갱신과 원장 기록이 원자적으로 반영되는 경우를 전제로 한다. 재시도와 동시 실행은 따로 검증해야 한다.

## 3. 단위 테스트부터 Job E2E까지 검증한다

복구 결과를 반복해서 확인하려고 실제 MySQL을 띄우는 통합 테스트 환경부터 만들었다. 연결 구성은 다음 순서다. 아래는 실행 코드 대신 역할만 나눠 그린 도식이다.

```text
MySQLContainer 시작
  → 컨테이너의 연결 정보로 Exposed Database 생성
  → 해당 Database를 명시한 transaction에서 테스트 실행
```

도입하면서 한 번 크게 넘어졌다. 테스트를 혼자 돌리면 통과하는데 전체 스위트에서는 실행 순서에 따라 실패했다. Exposed 트랜잭션의 기본 DB 선택에 기대고 있었기 때문이다. 각 테스트에서 쓸 `Database`를 명시하자 사라졌다. 컨테이너를 따로 띄우는 것과 애플리케이션이 그 DB를 사용하게 하는 것은 별개였다.

그 위에 세 층을 쌓았다. 기준은 각 층이 무엇을 볼 수 있고 무엇을 볼 수 없는지였다.

| 층 | 무엇을 검증하는지 | 도구 |
|---|---|---|
| 단위 | 정책 경계값(반올림, 시행일 전후) | DB·시계에 의존하지 않는 순수 함수 |
| 서비스 통합 | 원장 흐름: 재계산, 차액 반영, 멱등, 다일자 | 실제 MySQL Testcontainers |
| Job E2E | 배선·전파·복구: 실패가 Job으로 전파되는지, 복구가 완주하는지 | Spring Batch 실행계층 + Testcontainers |

계산식은 단위 테스트에서, Step 연결과 실패 전파는 Job E2E에서 확인했다. 모든 경계값을 E2E로 반복하기보다 각 층의 역할을 나눴다. 서비스 메서드를 직접 호출하는 테스트만으로는 Spring Batch가 최종 Job 상태를 어떻게 기록하는지 확인할 수 없었다.

구현 전에 실패하는 테스트부터 작성했다. 한 번은 테스트 데이터가 계산 상수의 배수여서 반올림 오류가 드러나지 않았다. 경계값을 포함한 데이터를 사용해야 기존 구현의 문제를 정확히 재현할 수 있었다.

새 테스트가 통과하면 구현을 의도적으로 이전 상태로 되돌려 실제로 실패하는지 확인했다.

```text
정상 계산: 차액 = 기대액 - 기존 금액
검증용 변형: 차액 = 기대액
기대 결과: 재실행 시 추가 반영을 금지하는 테스트가 실패
```

실패 전파도 같은 방식으로 확인했다. 집계 오류를 정상 반환으로 바꿔보면, 실패해야 할 Job이 `COMPLETED`가 된다. 테스트가 이 변형을 잡아야 실패 처리까지 검증했다고 할 수 있다. 변이 테스트 도구는 쓰지 않았고, 코드를 직접 바꿔 가며 확인했다.

한 번은 이전 구현으로 되돌려도 결과가 계속 통과로 표시됐다. 캐시를 비우고 다시 실행한 뒤 확인해 보니, 결과를 읽는 스크립트가 실패를 통과로 잘못 해석하고 있었다. 테스트뿐 아니라 결과를 수집하는 도구도 함께 검증해야 했다.

값이 실제로 바뀌는지 검증하려면 변경 전 상태부터 명시해야 했다.

```text
신규 복구: 기록 없음 확인 → 복구 실행 → 기대 기록 확인
정정 반영: 이전 값 확인 → 변경 입력 처리 → 수정된 값 확인
재실행: 현재 값 확인 → 같은 입력 재처리 → 추가 반영 없음 확인
```

최종값만 보면 신규 생성·정정·재실행이 구분되지 않는다. 변경 전 상태와 추가 기록까지 봐야 세 경우가 갈린다.

## 마무리

내가 바꾼 것은 누락을 처리하는 시점이었다. 실패한 날짜의 데이터를 한 번 채우고 끝내지 않고, 후속 실행이 그 날짜를 다시 읽는 경로를 만들었다. 재조회가 중복 반영을 만들지 않는지, 실패가 Job 상태에 드러나는지, 테스트가 실제 오류를 잡는지까지 확인해야 복구 설계를 검증했다고 말할 수 있었다.
