## 이미 처리한 줄 알았는데 숫자가 안 맞는다

외부 파트너에서 매일 주문/취소 리포트를 받아 사용자 적립 원장을 맞추는 배치가 있었다. 흐름은 단순하다.

1. 하루 한 번 전날 주문/취소 리포트를 가져온다.
2. 주문에서 적립액을 계산해 원장에 기록한다.
3. 취소가 오면 적립을 되돌린다.

그런데 일부 사용자의 적립이 취소 뒤에도 줄지 않았다. 코드를 보면 멱등성을 지키려는 의도는 분명했다.

```kotlin
fun sync(order: Order) {
    if (rewardHistoryRepo.existsById(order.key)) return   // 이미 처리했으면 건너뜀
    val reward = computeReward(order)
    rewardHistoryRepo.insert(order.key, reward)
    pointLedger.issue(order.userId, reward)
}
```

같은 리포트를 두 번 처리해도 중복 적립되지 않도록 `existsById`로 막았다. 문제는 **취소가 주문과 같은 날 오지 않는다**는 데 있었다.

```text
1차 실행: 주문 10,000 → 원장 key=100 저장
2차 실행: 같은 주문의 취소 도착
          → existsById(key) == true
          → "이미 처리함"으로 간주하고 종료
          → 취소가 반영되지 않는다
```

원장의 PK는 `(userId, orderId, 기준일)`이었다. 주문이 만든 행이 이미 존재하니, 다음 날 도착한 취소는 "이미 있는 키"에 막혀 계산조차 되지 않았다.

## 존재 여부는 입력의 동일성을 증명하지 않는다

여기서 멈춰 개념을 다시 봤다. `existsById(...) == true`가 증명하는 것은 딱 하나다.

> 이 키로 무언가 저장된 적이 있다.

증명하지 못하는 것은 이것이다.

> 지금 들어온 입력이 저장된 것과 같다.

배치가 멱등하려면 "같은 입력을 다시 처리해도 결과가 같아야" 한다. 그런데 이 시스템에서는 **같은 business key의 입력 자체가 나중에 바뀐다.** 어제의 "주문 10,000"이 오늘은 "주문 10,000 − 취소 3,000"이 된다. 입력이 변하는데 존재 여부로 skip하면, 변경분을 영구히 잃는다.

즉 **존재 확인은 멱등성의 대용이 될 수 없다.** 입력이 불변인 시스템에서만 성립하는 착각이다.

## 첫 시도는 틀렸다: 같은 실행 안에서만 맞춘 계산

처음 떠올린 수정은 "같은 실행 안에서 주문과 취소를 함께 계산하자"였다. 메모리에 그 실행의 적립을 누적해 취소 계산에 넘겼다.

이 방식은 두 테스트를 통과했다.

```text
주문 10,000 + 같은 실행의 전체취소 → 최종 0
주문 10,000 + 같은 실행의 부분취소 → 최종 70
```

하지만 더 깊은 반례가 남아 있었다.

```text
1차 실행: 주문 10,000        → 원장 100
2차 실행: (다음 날) 취소 도착
```

취소가 **다른 실행에 늦게** 오면, 메모리 누적은 아무 소용이 없다. 그 실행에는 원래 주문이 없기 때문이다. 그리고 여전히 `existsById`가 true라 계산 전에 종료됐다. 같은 실행 내부만 고친 국소적 수정이었다.

여기서 한 가지 더 배웠다. 테스트에서 트랜잭션을 두 번 열어 "다른 실행"을 표현했다고 생각했는데, 배치가 실행을 구분하는 기준은 **트랜잭션 개수가 아니라 데이터의 적재 시각**이었다. 늦게 도착한 변경을 재현하려면 테스트에서 적재 시각을 명시적으로 다르게 줘야 했다. 재현하지 못하는 반례는 고칠 수 없다.

## 제대로 된 해결: 기대 상태와의 차이만 반영한다

핵심을 바꿨다. **존재 여부가 아니라 값을 비교한다.** 원천 리포트를 재생해 "지금 이 주문이 있어야 할 기대 상태"를 만들고, 저장된 상태와의 **차이만** 부수효과로 흘려보낸다.

```kotlin
fun sync(triggerDate: LocalDate) {
    // 오늘 바뀐 주문의 활성 리포트 전체를 발생일 순서로 재생 → 현재 기대 상태
    val expected: Map<Key, Int> = replayActiveReports(triggerDate)
    val existing: Map<Key, Int> = rewardHistoryRepo.findByKeys(expected.keys)

    for ((key, expectedReward) in expected) {
        val storedReward = existing[key] ?: 0
        val delta = expectedReward - storedReward     // 부수효과는 '차이'만
        if (delta == 0) continue                       // 재실행 = no-op
        rewardHistoryRepo.upsert(key, expectedReward)  // 상태를 기대값으로 갱신
        pointLedger.adjust(key.userId, delta)          // +면 적립, −면 취소
    }
}
```

| 상황 | 기대 | 저장 | delta | 결과 |
|---|---|---|---:|---|
| 최초 주문 | 100 | 0 | +100 | 적립 |
| 늦은 부분취소 | 70 | 100 | −30 | 취소 |
| 늦은 전체취소 | 0 | 100 | −100 | 취소 |
| 동일 재실행 | 70 | 70 | 0 | no-op |

두 가지가 동시에 풀린다. 늦게 도착한 취소는 "기대 70 vs 저장 100 → −30"으로 반영되고, 같은 리포트를 다시 처리하면 "기대 = 저장 → delta 0 → no-op"이 된다. 존재 확인 한 줄로는 결코 얻을 수 없던 성질이다.

여기서 주의할 함정 하나. **부수효과에 기대값 자체를 쓰면 안 된다.** `pointLedger.adjust(userId, expectedReward)`처럼 기대값을 그대로 흘리면 재실행마다 이중 적립된다. 재실행 no-op을 만드는 것은 `expected − existing`이라는 차이다.

## 곁가지에서 함께 걸린 것들

문제를 파는 김에 같은 경로에서 세 가지를 더 고쳤다. 전부 "돈이 걸린 배치"에서 반복되는 패턴이다.

**PK가 하루 한 행을 강제하면, history는 이벤트 목록이 아니라 누적 상태다.** `(userId, orderId, 기준일)` PK 아래서는 같은 날의 변경을 여러 행으로 append할 수 없다. 그래서 history를 "그 날의 현재 상태"로 upsert하고 실제 `+100 / −30` 같은 움직임의 이력은 원장 쪽에 남겼다. 스키마를 못 바꾸는 상황에서 "상태 테이블"과 "이력 테이블"의 역할을 분리한 셈이다.

**DSL의 반환 계약을 확인해야 한다.** 커서 조건을 만드는 코드가 이랬다.

```kotlin
op.apply { this.and { cond } }   // ❌ 반환값을 버린다
```

여기서 쓴 라이브러리의 `and()`는 기존 객체를 변경하지 않고 **새 조건을 반환**한다. `apply`는 반환값을 무시하므로 조건이 조용히 사라졌고 커서가 전진하지 않아 매번 같은 구간을 다시 읽었다. 오류도, 예외도 없이 잘못된 결과만 나온다.

```kotlin
op = op.and { cond }             // ✅ 반환값을 다시 대입
```

**금전 누락은 성공으로 숨기지 않는다.** 사용자 매핑을 찾지 못했을 때 조용히 정상 반환하면, 원장에도 이력에도 아무것도 남지 않은 채 배치는 `성공`으로 끝난다. 이걸 예외로 올려 job을 실패로 남기도록 바꿨다. 돈이 빠진 실패는 시끄러워야 재처리와 조사가 가능하다.

## 정리

- **존재 확인(`existsById`)은 멱등성이 아니다.** 같은 business key의 내용이 나중에 바뀌는 시스템에서는 존재 여부가 아니라 **현재 기대 상태와의 일치**를 비교해야 한다.
- 멱등한 원장 갱신의 부수효과는 `기대상태 − 저장상태`다. 기대값 자체가 아니라 **차이**를 흘려보내야 재실행이 no-op이 된다.
- 기대 상태는 같은 실행 안의 메모리가 아니라 **원천을 재생**해서 만든다. 늦게 도착하는 변경은 실행 경계를 넘기 때문이다.
- 테스트는 실행을 트랜잭션 개수가 아니라 **적재 시각**으로 구분해야 늦은 변경을 재현할 수 있다.
- 곁가지: 상태 테이블과 이력 테이블의 역할 분리, DSL 반환 계약 확인, 금전 실패를 조용히 성공 처리하지 않기.

"이미 있으니 건너뛴다"는 배치에서 무언가 새는 느낌이 든다면, 그 키의 입력이 나중에 바뀔 수 있는지부터 의심해 보자.
