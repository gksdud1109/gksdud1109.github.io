> 실무에서 배운 판단 과정을 설명용 정산 모델로 재구성했다. 코드와 수치는 의사코드·가상 예시이며, 실제 스키마와 지급 정책을 나타내지 않는다.

## 이미 처리한 키인데 입력은 달라졌다

배치의 중복 처리를 막으려다 뒤늦게 도착한 변경까지 건너뛰는 문제를 다룬 적이 있다. 처음에는 같은 실행 안의 계산만 고쳤지만, 다른 실행에서 취소가 들어오는 반례를 해결하지 못했다. 그때 바꾼 판단 기준을 정산 예제로 설명한다.

주문과 취소를 받아 적립 내역을 계산하는 배치를 생각해 보자.

1. 하루 한 번 전날 주문/취소 리포트를 가져온다.
2. 주문에서 적립액을 계산해 원장에 기록한다.
3. 취소가 오면 적립을 되돌린다.

중복 적립을 막으려고 다음처럼 존재 여부를 검사하면 어떤 일이 생길까. 아래 함수들은 흐름을 설명하기 위한 의사코드다.

```kotlin
fun applyOnce(input: Input) {
    if (state.exists(input.key)) return
    val amount = calculate(input)
    state.save(input.key, amount)
    ledger.append(input.key, amount)
}
```

같은 리포트를 반복 처리할 때는 건너뛸 수 있다. 문제는 **취소가 주문과 같은 날 오지 않는다는 것**이다.

```text
1차 실행: 주문에 따른 적립 상태 100 저장
2차 실행: 같은 주문의 취소 도착
          → state.exists(key) == true
          → "이미 처리함"으로 간주하고 종료
          → 취소가 반영되지 않는다
```

이 예제의 키는 같은 주문의 상태를 찾는 식별자다. 취소가 도착해도 키는 같으므로, 이미 저장된 행이 있다는 이유로 변경분의 계산까지 건너뛴다. PK를 어떻게 구성했든 같은 문제가 생긴다.

## 존재 여부는 입력의 동일성을 증명하지 않는다

여기서 멈춰 개념을 다시 봤다. `exists(...) == true`가 증명하는 것은 딱 하나다.

> 이 키로 무언가 저장된 적이 있다.

증명하지 못하는 것은 이것이다.

> 지금 들어온 입력이 저장된 것과 같다.

배치가 멱등하려면 같은 입력을 다시 처리해도 결과가 같아야 한다. 그런데 이 예제에서는 같은 business key의 입력 자체가 나중에 바뀐다. 어제의 기대 적립액 100이 취소 후에는 70이 된다. 입력이 변하는데 존재 여부로 skip하면 변경분을 반영할 수 없다. 이 숫자는 계산 원리를 위한 가상 값이며, 구매액이나 지급 비율을 뜻하지 않는다.

주문 키의 존재 확인만으로는 바뀐 입력을 처리할 수 없다. 입력마다 고유한 이벤트 ID로 중복을 막는 것과, 상태가 바뀌는 주문 키로 건너뛰는 것은 서로 다른 문제다.

## 첫 시도는 틀렸다: 같은 실행 안에서만 맞춘 계산

처음에는 같은 실행 안에서 주문과 취소를 함께 계산하려 했다. 메모리에 그 실행의 적립을 누적해 취소 계산에 넘겼다.

이 방식은 두 테스트를 통과했다.

```text
최초 기대액 100 + 같은 실행의 전체취소 → 최종 0
최초 기대액 100 + 같은 실행의 부분취소 → 최종 70
```

하지만 더 깊은 반례가 남아 있었다.

```text
1차 실행: 주문 처리         → 적립 상태 100
2차 실행: (다음 날) 취소 도착
```

취소가 **다른 실행에 늦게** 오면 메모리 누적만으로는 원래 주문을 알 수 없다. 존재 확인으로 먼저 종료하는 문제도 그대로였다. 같은 실행 내부만 고친 수정이었다.

테스트에서도 같은 실수를 했다. 트랜잭션을 두 번 연다고 서로 다른 시점에 들어온 입력이 되지는 않는다. 적재 시각으로 입력을 고르는 배치라면 주문과 취소의 적재 시각을 다르게 넣어야 늦은 변경이 재현된다.

## 제대로 된 해결: 기대 상태와의 차이만 반영한다

판단 기준을 바꿨다. **존재 여부가 아니라 값을 비교한다.** 변경된 주문에 필요한 원천 기록을 다시 읽어 현재의 기대 상태를 계산하고, 저장된 상태와의 **차이만** 원장에 반영한다.

아래는 같은 DB 안에서의 계산과 기록을 설명하는 의사코드다. 전액 취소된 키도 기대값 0으로 계산 대상에 포함해야 한다.

```kotlin
fun reconcile(changedKeys: Set<Key>) {
    for (key in changedKeys) {
        transaction {
            val expected = calculateFromCurrentRecords(key)
            val existing = state.amountOrZero(key)
            val delta = expected - existing
            if (delta != 0) {
                state.save(key, expected)
                ledger.append(key, delta)
            }
        }
    }
}
```

| 상황 (각 행은 독립된 예시) | 기대 | 저장 | delta | 결과 |
|---|---|---|---:|---|
| 최초 주문 | 100 | 0 | +100 | 적립 |
| 늦은 부분취소 | 70 | 100 | −30 | 취소 |
| 늦은 전체취소 | 0 | 100 | −100 | 취소 |
| 동일 재실행 | 70 | 70 | 0 | no-op |

늦게 도착한 취소는 `기대 70 vs 저장 100 → −30`으로 반영된다. 같은 리포트를 순차적으로 다시 처리하면 `기대 = 저장 → delta 0 → no-op`이 된다.

원장에 기대값을 그대로 더하면 재실행할 때마다 이중으로 적립된다. 재실행해도 추가 반영이 생기지 않는 것은 `expected − existing`이라는 차이를 반영하기 때문이다.

위 예제는 같은 키의 처리가 직렬화되고, 상태 갱신과 원장 기록이 함께 커밋되거나 롤백된다고 전제한다. 동시에 실행되거나 외부 지급 API를 호출한다면 차액 계산과 별개로 동시성 제어와 중복 방지 설계가 필요하다.

## 곁가지에서 함께 걸린 것들

이 경험에서 함께 정리한 점이 세 가지 더 있다.

**현재 상태와 변경 이력은 역할이 다르다.** 키마다 한 행을 갱신하는 테이블은 현재 상태를 표현한다. `+100 / −30`처럼 변경 내역을 순서대로 남기는 테이블은 이력을 표현한다. `history`라는 이름의 테이블도 키마다 한 행을 갱신하는 구조일 수 있다. 기존 스키마를 유지해야 할 때도 이 구분부터 확인하는 편이 좋다.

**DSL의 반환 계약을 확인한다.** 조건을 추가할 때 실수하기 쉬운 형태는 이렇다.

```kotlin
op.apply { this.and { cond } }   // ❌ 반환값을 버린다
```

Exposed의 `and()`는 기존 객체를 변경하지 않고 **새 조건을 반환**한다. `apply`는 수신 객체를 돌려주므로, 그 안에서 만든 새 조건을 쓰지 않으면 필터가 추가되지 않는다. 커서 조건이라면 같은 구간을 다시 읽을 수 있다.

```kotlin
op = op.and { cond }             // ✅ 반환값을 다시 대입
```

**필수 데이터 누락을 정상 처리로 숨기지 않는다.** 계산에 필요한 매핑이 없는데 그대로 반환하면, 아무 기록도 남지 않은 채 Job이 성공할 수 있다. 실패로 중단할지 별도 오류 목록에 남길지는 정책에 따라 정하되, 처리되지 않은 입력이 정상 처리와 구분돼야 재조사할 수 있다.

## 정리

- **상태가 바뀌는 키는 존재 여부만으로 판단할 수 없다.** 같은 business key의 내용이 나중에 바뀌는 시스템에서는 현재 기대 상태와 일치하는지를 비교한다.
- 멱등한 원장 갱신의 부수효과는 `기대상태 − 저장상태`다. 원장에 **차이**만 반영해야 재실행이 no-op이 된다.
- 기대 상태는 같은 실행의 메모리 대신 **원천을 다시 읽어** 만든다. 늦게 도착하는 변경은 실행 경계를 넘기 때문이다.
- 늦은 변경을 테스트할 때는 트랜잭션을 나누는 것만으로 부족하다. **배치가 입력을 고를 때 보는 값**(적재 시각 등)도 다르게 넣어야 한다.
- 곁가지: 상태 테이블과 이력 테이블의 역할 분리, DSL 반환 계약 확인, 금전 실패를 조용히 성공 처리하지 않기.

이미 처리한 키를 건너뛰는 배치가 늦은 변경을 놓친다면, 그 키의 입력이 나중에 바뀔 수 있는지부터 보면 된다.
