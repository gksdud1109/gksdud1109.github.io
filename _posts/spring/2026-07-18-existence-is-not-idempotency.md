> 실무 정산 배치를 수정한 기록을 바탕으로 작성했다. 업무 식별자는 일반화했고, 아래 금액과 코드는 계산 흐름을 설명하기 위한 예시다.

주문과 취소 리포트를 받아 사용자 적립액을 계산하는 배치를 고쳤다. 취소를 반영하는 코드가 있었는데도 실제 결과에는 취소가 빠져 있었다. 처음에는 취소량의 부호만 바로잡으면 될 것으로 생각했다. 하지만 주문과 취소를 계산하는 순서, 이미 저장한 데이터를 다시 처리하는 방식까지 살펴봐야 했다.

원인을 설명하려면 먼저 날짜를 구분해야 한다. 이 배치는 매일 전날의 주문 리포트와 취소 리포트를 수집했다. 주문일과 취소일이 다르면 서로 다른 발생일의 기록으로 들어온다. 오래전 주문이 오늘 취소됐다고 해서 그 주문일의 리포트를 반드시 다시 가져와야 하는 구조는 아니었다.

## 취소 메서드는 양수를 받는데 음수를 넘겼다

기존 계산에서는 취소에 따른 적립 변동량을 음수로 표현했다. 반면 실제 차감을 수행하는 메서드는 **차감할 크기를 양수로 받는 계약**이었다. 아래는 당시 호출을 단순화한 것이다.

```kotlin
val rewardDelta = -30
cancelReward(amount = rewardDelta) // 내부에서는 amount > 0을 요구
```

음수를 넘기면 검증에서 실패했다. 그런데 적립 처리 Step은 폭넓은 예외를 skip하도록 설정돼 있었다. 취소 처리가 실패해도 Job 전체가 성공으로 끝날 수 있었고, 적립 결과만 보면 취소가 없었던 것처럼 남았다.

우선 음수 변동량을 차감 메서드의 양수 인자로 변환하고, 적립 계산 오류가 Job 실패로 드러나도록 수정해야 했다. 다만 이것만으로 계산 전체가 맞아지는 것은 아니었다.

## 같은 실행에서 계산한 적립을 DB에서는 아직 볼 수 없었다

주문과 취소를 함께 처리할 때의 기준값도 문제였다. 계산 단계에서 기존 적립액을 DB에서 읽었지만, 이번 실행에서 계산한 주문 적립액은 아직 Writer가 저장하기 전이었다.

```text
DB의 기존 적립: 0
이번 실행의 주문 계산: +100 → 아직 저장 전
이번 실행의 취소 계산: DB의 0을 기준으로 계산
```

주문을 처리한 뒤 취소를 계산한다고 생각했지만, 두 계산 사이에 DB 반영이 끝나는 구조가 아니었다. 같은 실행 안에서 만들어진 값을 DB 조회만으로 이어받으려 한 셈이다.

첫 수정에서는 메모리에 이번 실행의 적립을 누적해 취소 계산에 넘겼다. 같은 실행에서 주문과 전체 취소를 함께 넣으면 0, 부분 취소를 넣으면 남은 적립액이 나오도록 만들었다.

이 수정으로 그 실행의 계산은 맞출 수 있었다. 하지만 이후 재수집으로 입력이 바뀌었을 때도 맞는지는 별도로 확인해야 했다.

## 다른 날의 정상 취소와 같은 발생일의 정정은 다르다

기존 중복 검사 키에는 사용자·주문뿐 아니라 발생일도 포함돼 있었다. 따라서 다음 두 상황은 구분해야 한다.

| 상황 | 기존 키와의 관계 |
|---|---|
| 1일 주문이 3일에 취소됨 | 발생일이 달라 새 키로 처리 가능 |
| 1일 리포트를 다시 수집했더니 1일 기록이 수정됨 | 이미 처리한 발생일의 키와 겹칠 수 있음 |

첫 번째 상황까지 전부 “주문이 이미 있으니 취소를 건너뛰었다”라고 설명하면 실제 코드와 맞지 않는다. 여기서는 앞서 확인한 부호 계약과 계산 기준의 문제가 먼저다.

두 번째 상황에서는 존재 여부로 건너뛰는 방식의 한계가 드러난다. 저장된 키가 같아도 그 키의 입력 내용은 달라졌을 수 있다. 같은 발생일에 속하는 취소가 나중에 적재되는 반례를 테스트 데이터로 만들자, 이미 처리한 키라는 이유로 변경분을 반영하지 못했다. 이 테스트는 재처리 설계의 빈틈을 확인하기 위한 것이며, 모든 운영 취소가 이런 방식으로 들어왔다는 뜻은 아니다.

이 지점에서 이번 실행의 메모리를 더 보완하기보다, 저장된 원천 기록으로 결과를 다시 계산하는 쪽으로 바꿨다.

## 주문별 원천 기록을 발생일 순서로 다시 계산했다

변경된 주문에 대해 현재 유효한 주문·취소 기록을 모으고, 발생일 순서로 누적 순구매액을 계산했다. 그 누적액에 지급 정책을 적용해 각 시점의 기대 적립액을 구했다.

```text
누적 순구매액
  → 그 시점까지 받아야 할 누적 적립액
  → 직전 시점과의 차이 = 해당 발생일의 기대 변동량
  → DB에 저장된 같은 발생일의 변동량과 비교
  → 차이만 추가 반영
```

일별 구매액에 각각 정책을 적용해 더하는 방식과 누적액에 정책을 적용하는 방식은 반올림 경계에서 결과가 달라질 수 있다. 이 배치에서는 누적 순구매액을 기준으로 계산을 통일했고, 적용 정책은 최초 주문일을 기준으로 정했다. 재실행하는 날짜가 달라졌다고 과거 주문의 정책까지 바뀌어서는 안 됐다.

또 앞선 발생일이 정정되면 이후의 누적액도 달라진다. 그래서 새로 적재된 날짜만 계산하지 않고, 해당 주문의 발생일별 기대 변동량을 다시 비교했다.

핵심 반영 로직을 단순화하면 다음과 같다. `expected`와 `existing`은 모두 같은 발생일에 저장할 변동량이다.

```kotlin
transaction {
    for ((date, expected) in recalculateByDate(order)) {
        val existing = rewardState.findAmount(order.id, date) ?: 0
        val adjustment = expected - existing

        rewardState.upsert(order.id, date, expected)

        when {
            adjustment > 0 -> issueReward(adjustment)
            adjustment < 0 -> cancelReward(-adjustment)
        }
    }
}
```

원천 기록을 다시 읽는 것은 기대값을 구하기 위해서이고, 차액을 구하는 것은 이미 반영한 금액을 또 지급하지 않기 위해서다.

| 처리 | 기대 변동량 | 저장된 변동량 | 이번 추가 반영 |
|---|---:|---:|---:|
| 최초 주문 적립 | +100 | 0 | +100 |
| 같은 발생일의 입력 정정 | +70 | +100 | −30 |
| 같은 입력으로 재실행 | +70 | +70 | 0 |
| 별도 발생일의 취소 신규 반영 | −30 | 0 | −30 |

마지막 행은 앞의 정정 예시와 독립된 경우다. 두 경우 모두 차감 메서드에는 양수 30을 넘기지만, 어느 발생일의 저장값과 비교하는지는 다르다.

## 검증도 실행 경계를 나눠서 했다

같은 실행에서 주문과 취소를 함께 넣는 테스트에 더해, 주문을 먼저 반영하고 나중에 변경된 원천 기록을 적재하는 테스트를 추가했다. 배치가 적재 시각으로 대상을 고르므로, 두 트랜잭션을 여는 것뿐 아니라 입력의 적재 시각도 다르게 줬다.

확인한 것은 전체 취소·부분 취소의 결과, 발생일이 다른 취소, 같은 발생일 데이터의 정정, 그리고 재실행 시 추가 반영이 없는지였다. 수정한 차액 계산을 예전처럼 기대값 그대로 반영하도록 되돌리면 재실행 테스트가 실패하는지도 확인했다.

이 방식은 같은 주문의 처리가 직렬화되고, 적립 상태 갱신과 차액 반영이 같은 DB 트랜잭션에 묶인다는 전제다. 외부 지급 API까지 포함한 중복 방지를 이 계산식만으로 해결한 것은 아니다.

처음에는 취소 계산 한 군데를 고치는 작업이라고 생각했다. 실제로는 취소 인자의 계약을 바로잡고, 저장 전 계산값에 의존하던 흐름을 걷어낸 뒤, 바뀐 입력을 다시 처리해도 추가 지급이 생기지 않게 만들어야 했다. 원천을 다시 읽을 수 있게 되면서, 다음에는 [실패한 날짜를 후속 실행이 다시 수집하는 문제](/posts/self-healing-settlement-batch/)를 다룰 수 있었다.
