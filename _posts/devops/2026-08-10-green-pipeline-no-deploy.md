수정한 코드를 머지하고 빌드하고 배포했다. 파이프라인은 전부 초록이었다. 그런데 검증 지표가 옛날 값 그대로였다.

```bash
curl -s "$BASE/attachments" -H "Authorization: Bearer $JWT" \
  | jq -r '.[0].imageUrls[0]' | grep -o 'X-Amz-Expires=[0-9]*'
# → X-Amz-Expires=600    (기대: 3600)
```

만료 시간을 1시간으로 바꾼 코드가 서비스에 아직 안 붙었다.

## 일단 확인부터 했다

- CI 워크플로: 전부 성공
- 컨테이너 레지스트리: 새 이미지 push 완료
- 개발 브랜치: 머지 확인, 코드에 `readUrlExpiration = Duration.ofHours(1)` 존재

코드도 있고 이미지도 있고 파이프라인도 성공했다. 그런데 서비스는 여전히 옛날 동작을 했다.

## diff가 없으니 배포도 없었다

배포는 Terraform이 ECS task definition을 갱신해서 이뤄졌다. 이미지 태그로는 가변 태그를 썼다.

```text
terraform 목표 상태: image = ...:dev-latest
현재 상태:           image = ...:dev-latest
→ diff 없음 → 새 task definition 리비전 없음 → 서비스 업데이트 없음 → 배포 미발생
```

레지스트리에서 `dev-latest`가 가리키는 이미지가 바뀌어도 **이미 떠 있는 태스크는 다시 받지 않는다.** 태스크는 기동 시점에 pull한 이미지를 계속 서빙한다. 게다가 워크플로에 강제 재배포 옵션이 빈 배열로 꺼져 있어서 우회할 방법도 없었다.

**가변 태그는 선언적 IaC와 상성이 나쁘다.** 상태를 비교해서 움직이는 도구는 이름이 그대로면 내용이 바뀌어도 안 바뀐 걸로 본다.

## 불변 태그로 바꿨다

이미지 태그에 커밋 SHA를 넣어 이미지 URI 자체가 달라지게 했다.

```bash
echo "dev-$(git rev-parse origin/develop)"
```

빌드 워크플로가 이미 `<environment>-<github.sha>` 형식으로 태그를 만들고 있어서 새로 만들 것도 없었다. 이 값을 배포 변수로 넘기면 URI가 달라지고 새 task definition 리비전이 생기고 롤링 배포가 돌고 새 이미지를 pull한다. 제대로 됐는지는 배포 로그에서 task definition 리소스가 새 리비전으로 교체되는지 보면 된다.

## digest와 tag를 헷갈렸다

여기서 한 번 돌아갔다. `docker push` 출력이 이렇게 생겼다.

```text
dev-latest: digest: sha256:9dbe... size: 2616
```

이 출력만 보고 digest가 배포에 넣을 태그인 줄 알았다.

- **tag**는 `dev-latest`다. 배포 변수에 넣는 값이다.
- **digest**는 `sha256:9dbe...`다. 이미지 내용의 해시이고 여기서는 쓰지 않는다.

빌드 워크플로는 태그를 두 개 민다. 로그에서 `dev-latest` 줄 **바로 위**에 `dev-<sha>` 줄이 있었다. 필요한 값은 처음부터 로그에 찍혀 있었다.

## 배포 검증 지표를 코드에 심어 뒀다

이번 건에서 가장 값진 소득이다. 우연히 얻은 패턴인데 앞으로도 쓸 만하다.

이번에 바꾼 값은 presigned URL의 만료 시간이었고 그 값이 API 응답에 그대로 드러났다. 그래서 응답 한 줄이 배포가 됐는지 안 됐는지 가르는 지표가 됐다.

| 관측값 | 의미 |
|---|---|
| `X-Amz-Expires=3600` | 새 이미지가 실제로 떴다 |
| `X-Amz-Expires=600` | 배포 미반영. 코드 문제가 아니다 |

이게 없었다면 코드를 다시 뒤지고 있었을 것이다. 실제로 처음 의심한 것도 코드 쪽이었다.

**파이프라인이 성공했으니 배포됐겠지를 믿지 말고 런타임에 찍히는 값으로 확인한다.** 그리고 가능하면 그 값이 드러날 자리를 미리 만들어 둔다. 바꾼 값이 API 응답이나 로그에 드러난다면 그게 곧 검증 지표다.

## 같은 스크립트라도 넘기는 변수가 성격을 바꾼다

곁가지로 하나 더 밟았다. 배포 워크플로가 두 개 있었는데 둘 다 같은 apply 스크립트를 실행한다. 차이는 넘기는 변수뿐이다.

| 변수 | apply 워크플로 | deploy 워크플로 |
|---|---|---|
| 기능 모듈 활성화 | `false` | `true` |
| 기능 활성화 허용 | `false` | `true` |
| 성격 | 기능이 꺼진 baseline 인프라 | 기능을 켜고 앱 배포 |

이름만 보고 apply를 돌리면 모듈 비활성화 값이 그대로 박혀서 **기능 전체가 꺼지는 회귀**가 난다. 워크플로 이름이 아니라 넘기는 변수를 봐야 한다.

배포 순서도 정리해 뒀다.

```text
① DDL 마이그레이션 (필요 시)
② 애플리케이션: PR 머지 (base 브랜치 확인)
③ 애플리케이션: 이미지 빌드 및 push → <env>-<sha>
④ IaC 변경이 있으면 커밋 및 push
⑤ IaC: deploy 워크플로 (image_tag = <env>-<sha>)
⑥ 런타임 지표로 검증
```

## 공통 값이 기능 A 블록에 갇혀 있었다

같은 작업에서 별개 문제를 하나 더 찾았다. 환경 변수 주입이 이렇게 돼 있었다.

```hcl
var.feature_a_bucket_name == null ? [] : [
  { name = "AWS_REGION", ... },      # ← 기능 A 블록 안에 갇힘
  { name = "FEATURE_A_BUCKET", ... },
]
```

개발 환경은 기능 A의 버킷 변수가 null이라 **블록 전체가 스킵되면서 공통 값인 리전까지 함께 증발**했다. 기능 B는 리전을 못 받았다.

공통 값을 조건에서 떼어냈다.

```hcl
(feature_a == null && feature_b == null) ? [] : [ { name = "AWS_REGION", ... } ],
feature_a == null ? [] : [ { name = "FEATURE_A_BUCKET", ... } ],
feature_b == null ? [] : [ { name = "FEATURE_B_BUCKET", ... } ],
```

**여러 기능이 공유하는 값을 한 기능의 조건부 블록에 넣으면 그 기능을 끄는 순간 다른 기능이 조용히 깨진다.** 꼭 필요한 값을 곁가지에 매달아 둔 셈이다.

## 기각한 가설

| 의심 | 확인 결과 |
|---|---|
| 코드가 머지되지 않았다 | 머지됨. 변경된 상수까지 확인 |
| 빌드가 실패했다 | 성공. 레지스트리에 이미지 존재 |
| digest를 태그로 넣어야 한다 | digest는 배포에 쓰지 않음 |
| 런타임 설정이 값을 덮어썼다 | 설정 계약에 없는 프로퍼티라 해당 없음 |
| 가변 태그라 diff가 없었다 | 원인 확정 |

앞의 네 개는 전부 애플리케이션 쪽 의심이었다. 파이프라인이 성공했다는 이유로 배포 계층을 아예 후보에서 뺐다.

## 정리

1. **파이프라인이 초록이라고 배포된 게 아니다.** 런타임에서 값을 봐야 닫힌다.
2. **선언적 도구에는 불변 식별자를 줘야 한다.** `latest` 같은 가변 태그는 상태 비교를 무력화한다.
3. **같은 스크립트라도 넘기는 변수가 성격을 바꾼다.** 워크플로 이름만 보고 고르면 회귀를 만든다.
4. **여러 기능이 쓰는 값은 특정 기능의 조건부 블록 밖에 둔다.**

배포가 안 됐는데 초록인 상황은 코드를 아무리 봐도 답이 안 나온다. 검증 지표를 코드에 심어두면 그 구간을 몇 초 만에 가른다.
