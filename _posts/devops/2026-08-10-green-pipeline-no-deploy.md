```text
실제 응답: X-Amz-Expires=600
기대 응답: X-Amz-Expires=3600
```

처음에는 코드가 잘못됐거나 설정이 덮어쓰는지 의심했다. 하지만 변경 코드는 브랜치에 있었고 ECR에도 새 이미지가 올라가 있었다. 빌드 이후 실행 중인 ECS 태스크까지 이어지는 경로를 확인해야 했다.

## ECR의 태그는 바뀌었지만 Terraform의 입력은 같았다

당시 배포는 Terraform으로 ECS task definition과 서비스를 갱신하는 방식이었다. 이미지 입력에는 `dev-latest`라는 가변 태그를 사용했다.

새 빌드가 같은 태그를 덮어써도 Terraform에 전달되는 이미지 URI는 같았다. 다른 변경도 없어 새 task definition을 만들거나 서비스를 다시 배포할 계기가 없었다.

```text
이전 task definition: image = repository:dev-latest
이번 Terraform 입력: image = repository:dev-latest
                      ↓
                 이미지 URI 변경 없음
                      ↓
           해당 변경으로 인한 새 배포 없음
```

이미 실행 중인 컨테이너가 레지스트리의 태그 변경을 계속 따라가는 것은 아니다. 새 이미지를 push했다는 사실만으로 기존 태스크가 교체되지는 않았다.

가변 태그로 배포하는 것 자체가 불가능한 것은 아니다. ECS는 같은 태그를 유지하면서도 `forceNewDeployment`로 새 태스크를 띄울 수 있다. 당시 실행 경로에서는 그 재배포가 요청되지 않았고, 이미지 URI도 바뀌지 않은 것이 문제였다. [ECS UpdateService 문서](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_UpdateService.html)

## 이미 만들어진 SHA 태그를 배포 입력으로 넘겼다

빌드 워크플로를 보니 같은 이미지를 두 태그로 push하고 있었다.

```text
dev-latest
dev-<빌드한 커밋의 전체 SHA>
```

따라서 빌드를 다시 설계할 필요는 없었다. **배포하려는 빌드 실행이 출력한 SHA 태그**를 IaC의 이미지 입력에 넘기면 됐다. 이전 빌드와 URI가 달라지면서 task definition 갱신과 서비스 배포로 이어졌다.

여기서 주의할 점은 브랜치의 최신 SHA를 임의로 읽어 쓰지 않는 것이다. 브랜치가 더 진행됐거나 빌드한 ref가 다르면, 그 SHA의 이미지가 아직 없을 수 있다. 실제 빌드가 사용한 커밋과 ECR에 올라간 태그를 연결해야 했다.

```text
빌드 실행의 커밋 SHA
  → 그 실행에서 push한 env-SHA 태그
  → IaC 배포 입력
  → 새 task definition
  → ECS 서비스의 새 태스크
```

SHA가 붙은 태그도 레지스트리에서 덮어쓸 수 있다면 절대적인 불변 식별자는 아니다. 같은 태그를 다른 내용으로 덮어쓰지 않는 운영 규칙이 필요하고, 이미지 내용을 직접 고정하려면 digest를 사용할 수 있다.

## tag와 digest는 모두 이미지 식별에 쓸 수 있다

처음에는 push 로그에 나온 `sha256:...`를 태그 입력란에 넣어야 하는지 헷갈렸다. 구분해야 할 것은 값의 모양과 받는 쪽의 계약이었다.

```text
태그로 참조: repository:dev-<commit-sha>
내용으로 참조: repository@sha256:<image-digest>
```

당시 입력 변수는 태그를 받아 `repository:tag`를 만드는 형태였다. 그 자리에 digest 문자열만 넣는 것은 맞지 않았다. digest를 배포에 쓸 수 없다는 뜻은 아니다.

이후 IaC에는 태그로 이미지를 조회한 뒤 digest를 사용해 URI를 결정하는 경로도 들어갔다. 이 글에서 다루는 문제는 그 이전에, 같은 가변 URI를 전달하고 새 배포도 요청하지 않았던 실행이다.

## 워크플로의 성공과 서비스 반영을 따로 확인했다

새 태그를 지정한 배포 뒤 API 응답의 만료 시간이 3600으로 바뀌는 것을 확인했다. 이 값은 이번 코드 변경이 서비스에서 동작하는지 확인하기에 유용했다.

다만 응답값 하나로 어떤 이미지가 실행됐는지까지 증명할 수는 없다. 설정이나 캐시도 동작에 영향을 줄 수 있으므로, 배포 확인 순서를 다음처럼 정리했다.

| 단계 | 확인할 것 |
|---|---|
| 빌드 | 어느 커밋으로 어떤 태그·digest를 push했는가 |
| 배포 입력 | 의도한 이미지 식별자가 task definition에 들어갔는가 |
| ECS 서비스 | 새 배포가 진행되고 원하는 task definition의 태스크가 실행되는가 |
| 컨테이너 | 실행 중인 imageDigest가 의도한 이미지와 맞는가 |
| 기능 | 이번에 바꾼 API 동작이 실제로 나타나는가 |

배포 워크플로가 넘기는 기능 활성화 변수도 확인했다. 같은 Terraform 스크립트를 실행해도 입력값에 따라 결과 구성이 달랐기 때문이다. 실행 이름만 확인해서는 어떤 상태를 적용했는지 알 수 없었다.

이번에는 만료 시간이라는 작은 값 덕분에 변경 미반영을 빨리 발견했다. 이후에는 빌드 산출물과 배포 입력, 실행 중인 태스크, 변경한 동작을 순서대로 연결해 확인하는 기준으로 삼았다. CI가 성공했다는 결과만 보던 때보다 문제가 끊긴 위치를 훨씬 좁혀 볼 수 있었다.
